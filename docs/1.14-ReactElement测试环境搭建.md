# React 测试环境搭建与 test-utils 实现

## 第一部分：顶层鸟瞰

### 背景问题

在 React 开发过程中，需要搭建一套完整的测试环境来验证 ReactElement 的功能。本文实现了第三种调试方式——用例调试，需要解决以下核心问题：
- 如何配置适合 React 的测试环境（使用 ReactDOM 作为宿主环境）
- 如何打包测试工具库（test-utils）供测试用例使用
- 如何配置 Jest 测试框架与测试脚本
- 如何处理模块依赖关系（external 配置）

**核心挑战：**
- 需要单独打包 test-utils 模块，并正确处理其对 react-dom 和 react 的依赖
- 需要配置 Jest 使用 jsdom 作为测试环境，模拟 DOM 环境
- 需要配置 Rollup 正确编译和打包测试工具，并修改 UMD 模块名称
- 需要设置正确的模块路径和忽略规则
- 需要安装缺失的依赖（@rollup/plugin-alias）

## 第三部分：主要知识点

### 1. ReactElement 测试用例的三种调试方式

本节课实现第三种调试方式——用例调试，包含三部分内容：
- 实现第一个测试工具 test-utils
- 实现测试环境
- 实现 ReactElement 用例

与测试相关的代码都来自 React 仓库，可以先把 React 仓库下载下来：

```bash
git clone git@github.com:facebook/react.git
```

### 2. test-utils 工具集

这是用于测试的工具集，来源自 ReactTestUtils.js，特点是：使用 ReactDOM 作为宿主环境。

### 3. 测试环境配置

测试环境使用 jsdom。

**安装命令：**
```bash
pnpm add -D jest@29.3.1 jest-config@29.3.1 jest-environment-jsdom@29.3.1 -w
```

**配置说明：**

```javascript
const { defaults } = require('jest-config');

module.exports = {
  ...defaults,
  rootDir: process.cwd(),
  modulePathIgnorePatterns: ['<rootDir>/.history'],
  moduleDirectories: [
    // 对于 React ReactDOM
    'dist/node_modules',
    // 对于第三方依赖
    ...defaults.moduleDirectories
  ],
  testEnvironment: 'jsdom'
};
```

**关键配置解释：**
- `testEnvironment: 'jsdom'`：使用 jsdom 模拟浏览器 DOM 环境
- `moduleDirectories`：配置模块查找路径，对于 React 和 ReactDOM 从 dist/node_modules 中加载，对于第三方依赖从 node_modules 加载
- `rootDir: process.cwd()`：设置根目录为当前工作目录
- `modulePathIgnorePatterns`：忽略 .history 目录下的文件

### 4. Rollup external 配置的作用

在 test-utils 的打包配置中，使用了 `external: ['react-dom', 'react']`，这表示：
- 这些依赖不会被打包进 test-utils.js
- 运行时需要外部提供这些依赖
- 减小打包体积，避免重复打包

### 5. UMD 格式的优势

所有打包输出都使用了 UMD（Universal Module Definition）格式：
- 支持 AMD 模块加载器
- 支持 CommonJS 模块系统
- 支持浏览器全局变量
- 通用性强，适合库的分发

### 6. globals 配置的作用

在 test-utils 的打包配置中，使用了 `globals` 配置：

```javascript
output: [{
  // ...
  globals: {
    react: 'React',
    'react-dom': 'ReactDOM'
  }
}]
```

**作用：** 告诉 Rollup，当 test-utils 以 UMD 格式在浏览器中运行时，外部依赖 `react` 和 `react-dom` 应该从全局变量 `React` 和 `ReactDOM` 中获取。

**为什么需要？**
- UMD 格式需要知道外部依赖的全局变量名
- 避免构建时的警告："Missing global variable names"
- 确保在浏览器环境中正确引用外部依赖

### 7. @rollup/plugin-alias 的作用

在 react-dom.config.js 的开头导入了这个插件：

```javascript
import alias from '@rollup/plugin-alias';
```

**作用：** 配置模块路径别名，在打包时将特定的模块路径映射到实际的文件路径。

**使用场景：**
```javascript
alias({
  entries: {
    hostConfig: `${pkgPath}/src/hostConfig.ts`
  }
})
```

这样代码中 `import xxx from 'hostConfig'` 就会被解析为实际的文件路径。

**为什么之前能正常打包？**
- 可能之前手动安装过，但没有保存到 package.json
- 或者 node_modules 中碰巧有这个包（作为其他包的依赖）
- 本次正式添加到 devDependencies 中，确保项目依赖完整

### Q1：`"test": "jest --config scripts/jest/jest.config.js"` 是什么意思

<details>
<summary>点击查看答案</summary>

这条命令包含三个部分：

```bash
jest --config scripts/jest/jest.config.js
```

| 部分 | 含义 |
|------|------|
| `jest` | 运行 jest 测试工具（自动化测试框架） |
| `--config` | 告诉 jest 使用自定义配置文件 |
| `scripts/jest/jest.config.js` | 配置文件的路径 |

---

**完整理解：**

当你在 package.json 中写：
```json
{
  "scripts": {
    "test": "jest --config scripts/jest/jest.config.js"
  }
}
```

然后在终端运行：
```bash
pnpm test
```

实际执行的就是：
```bash
jest --config scripts/jest/jest.config.js
```

---

**jest 是什么？**

jest 是一个测试框架，用来自动运行测试用例并检查代码是否正确。

**例子：**
```javascript
// 测试用例
test('React 能正常创建元素', () => {
  const element = React.createElement('div');
  expect(element.type).toBe('div');
});
```

jest 运行后会告诉你测试是否通过。

---

**为什么需要 `--config` 指定配置文件？**

因为我们的项目有特殊需求：
1. 需要从 `dist/node_modules` 加载我们自己打包的 React 版本
2. 需要 jsdom 环境（模拟浏览器 DOM）
3. 需要忽略某些文件夹（.history）

如果用 jest 默认配置，不知道这些特殊要求，测试就会失败。所以我们在 `scripts/jest/jest.config.js` 里写了自定义配置，然后通过 `--config` 参数告诉 jest 使用这个配置。

---

**总结：**

`"test": "jest --config scripts/jest/jest.config.js"` 的意思是：
- 运行 jest 测试框架
- 使用 `scripts/jest/jest.config.js` 这个自定义配置文件
- 这样 jest 就知道如何正确加载和测试我们的 React 代码

</details>

### Q2：`scripts/jest/jest.config.js` 每一行的含义和作用是什么

<details>
<summary>点击查看答案</summary>

配置文件：
```javascript
/* eslint-disable @typescript-eslint/no-var-requires */
const { defaults } = require('jest-config');
module.exports = {
  ...defaults,
  rootDir: process.cwd(),
  modulePathIgnorePatterns: ['<rootDir>/.history'],
  moduleDirectories: [
    // 对于 React ReactDOM
    'dist/node_modules',
    // 对于第三方依赖
    ...defaults.moduleDirectories
  ],
  testEnvironment: 'jsdom'
};
```

逐行解释：
1. `/* eslint-disable @typescript-eslint/no-var-requires */`
   - 关闭 ESLint 对 `require` 的限制规则。
   - 因为这个文件使用 CommonJS 写法（`require`），否则会报 lint 警告。
2. `const { defaults } = require('jest-config');`
   - 从 `jest-config` 拿到 Jest 默认配置。
   - 作用是后面可以基于默认配置做增量修改，不用全量重写。
3. `module.exports = { ... }`
   - 把这个对象导出给 Jest 使用。
   - Jest 启动时会读取这里的内容作为测试规则。
4. `...defaults,`
   - 先继承官方默认配置。
   - 后面同名字段会覆盖默认值。
5. `rootDir: process.cwd(),`
   - 将项目根目录设为“当前命令执行目录”。
   - 后续 `<rootDir>` 占位符都基于这个目录解析。
6. `modulePathIgnorePatterns: ['<rootDir>/.history'],`
   - 告诉 Jest 忽略 `.history` 目录。
   - 避免把编辑器历史文件当作测试输入，减少干扰。
7. `moduleDirectories: [ ... ]`
   - 配置模块查找路径顺序（例如 `import 'react'` 去哪里找）。
8. `'dist/node_modules',`
   - 优先从 `dist/node_modules` 找模块。
   - 这样测试会用你自己打包出来的 `react/react-dom`，不是外部现成包。
9. `...defaults.moduleDirectories`
   - 保留默认模块目录（通常含 `node_modules`）。
   - 保证第三方依赖仍可正常解析。
10. `testEnvironment: 'jsdom'`
    - 指定测试环境为 `jsdom`（浏览器模拟环境）。
    - 提供 `window/document` 等 API，支持 React DOM 相关测试。


总结：这个文件的本质是“Jest 测试运行规则清单”。它决定了测试在哪个环境跑、从哪里加载模块、忽略哪些目录。

</details>

### Q3：为什么 `react-dom.config.js` 和 `react.config.js` 要把 `name` 改成 `ReactDOM`、`client`、`React`

<details>
<summary>点击查看答案</summary>

先区分两个概念：

1. `file`：输出文件名（磁盘路径），例如 `index.js`、`client.js`
2. `name`：UMD/IIFE 场景下的模块名（全局变量标识），例如 `ReactDOM`、`React`

所以这次改动的核心不是改文件名，而是改“模块对外名字”。

---

为什么不能继续用 `index.js` / `client.js` 作为 `name`？

- `index.js`、`client.js` 这种更像文件名，不是清晰的库标识
- 在 UMD 的全局模式下，`name` 会影响对外暴露和依赖匹配
- 用标准库名（`ReactDOM`、`React`）可读性和一致性更好

---

为什么 `name: 'client'` 也要去掉 `.js`？

- `client.js` 是文件名（`file` 字段负责）
- `client` 是模块标识（`name` 字段负责）
- 模块标识通常不带扩展名，语义更清晰

---

你提到的点是对的：UMD 不只用于浏览器。

UMD 目标是兼容多种模块系统（CommonJS / AMD / 全局变量）。  
其中 `output.name` 主要影响的是“全局变量模式”（以及类似 IIFE 的全局挂载场景），在这类场景下名字是否规范会直接影响可用性。

---

为什么要用 `ReactDOM` / `React` 这种标准名？

因为你的配置里还存在依赖映射关系（例如 `globals`）：

- `react` 对应 `React`
- `react-dom` 对应 `ReactDOM`

如果主包名字是随意的（例如 `index.js`），就容易出现“依赖方按 `ReactDOM` 找，全局实际暴露却不是这个名字”的错配风险。

---

总结：

把 `name` 从 `index.js/client.js` 改成 `ReactDOM/client/React`，本质是在做两件事：
1. 从“文件名思维”切换到“模块标识思维”
2. 让 UMD 多环境下（尤其全局模式）命名一致，减少依赖解析和对接风险

</details>

### Q4：`react-dom/test-utils.ts` 会被 Jest 自动调用吗？

<details>
<summary>点击查看答案</summary>

先把这个问题拆成三步：

**第1步：这个文件本身在做什么？**

`react-dom/test-utils.ts` 提供了一个测试辅助函数，用来把 React 元素渲染到临时 DOM 容器。

```typescript
export function reenderIntoContainer(element: ReactElementType) {
  const div = document.createElement('div');
  createRoot(div).render(element);
}
```

作用是把“创建容器 + createRoot + render”这段重复逻辑抽出来，测试里可以复用。

---

**第2步：它为什么依赖 `jsdom`？**

因为里面调用了：

```typescript
document.createElement('div')
```

Jest 默认是 Node 环境，Node 没有 `document`。  
所以必须在 `jest.config.js` 里配置：

```javascript
testEnvironment: 'jsdom'
```

否则会报：`ReferenceError: document is not defined`。

---

**第3步：它会被 Jest 自动调用吗？**

不会。

Jest 自动做的是：
1. 找到测试文件（例如 `*.test.js`、`__tests__` 目录）
2. 执行测试文件里的代码

`test-utils.ts` 只有在测试代码手动引入并调用时才会执行：

```javascript
import { reenderIntoContainer } from 'react-dom/test-utils';
reenderIntoContainer(<App />);
```

---

总结：
- `test-utils.ts`：测试辅助工具（负责渲染到容器）
- `jsdom`：提供 `document/window`（让工具可运行）

### Q5：为什么 test-utils 要设置 `external: ['react-dom', 'react']`？

### Q6：为什么 ReactDOM 要输出多个文件？

<details>
<summary>点击查看答案</summary>

ReactDOM 打包后会输出5个文件：

1. `index.js` (ReactDOM 主包)
2. `client.js`
3. `jsx-runtime.js`
4. `jsx-dev-runtime.js`
5. `test-utils.js`

各文件的作用和使用场景：

| 文件 | 作用 | 使用场景 |
|------|------|---------|
| **index.js** | ReactDOM 主包 | `import ReactDOM from 'react-dom'` |
| **client.js** | 客户端渲染 | `import { createRoot } from 'react-dom/client'` |
| **jsx-runtime.js** | JSX 运行时（生产） | Babel/SWC 编译 JSX 时自动引用 |
| **jsx-dev-runtime.js** | JSX 运行时（开发） | 开发模式下的 JSX 编译 |
| **test-utils.js** | 测试工具 | 测试用例中使用 |

---

为什么要分开？

1. **按需加载**：用户只引用需要的部分，减小打包体积
2. **环境区分**：开发环境和生产环境使用不同的 JSX 运行时
3. **功能分离**：测试工具只在测试时使用，不影响生产代码

---

使用示例：

```javascript
// 用户代码
import { createRoot } from 'react-dom/client';  // 使用 client.js

// JSX 编译后（生产环境）
import { jsx } from 'react/jsx-runtime';  // 使用 jsx-runtime.js

// 测试代码
import { reenderIntoContainer } from 'react-dom/test-utils';  // 使用 test-utils.js
```

### Q7：如何理解 external 机制？

<details>
<summary>点击查看答案</summary>

用生活例子来理解：

想象你要组装一台电脑：

**方案1（不用 external）：**
```
显卡公司：我把电源、散热器、线材全部给你打包好
→ 你收到一个巨大的包裹，里面什么都有
→ 但你家里已经有电源和散热器了，浪费了！
```

**方案2（用 external）：**
```
显卡公司：我只给你显卡本体，电源和散热器你自己准备
→ 包裹很小，只有显卡
→ 你用家里现成的电源和散热器连接
→ 省钱、省空间、不重复
```

---

回到代码：

**不用 external（错误）：**

```javascript
// Rollup 配置
{
  input: 'test-utils.ts',
  output: { file: 'test-utils.js' }
  // 没有 external
}

// 结果：test-utils.js 包含了所有依赖
test-utils.js (2MB)
  ├─ test-utils 自己的代码 (10KB)
  ├─ react-dom 的代码 (1MB)
  └─ react 的代码 (1MB)
```

**用 external（正确）：**

```javascript
// Rollup 配置
{
  input: 'test-utils.ts',
  output: { file: 'test-utils.js' },
  external: ['react-dom', 'react']  // 告诉 Rollup：这些不打包
}

// 结果：test-utils.js 很小
test-utils.js (10KB)
  └─ test-utils 自己的代码 (10KB)
  
// react-dom 和 react 从外部引用
// Jest 会从 dist/node_modules 中加载
```

---

运行时如何工作：

```javascript
// test-utils.js 编译后（使用 external）
(function (global, factory) {
  typeof exports === 'object' && typeof module !== 'undefined' 
    ? factory(exports, require('react-dom'), require('react'))  // ← 外部引用
    : // ...
})(this, function (exports, reactDom, react) {
  // test-utils 的代码
  // 使用 reactDom 和 react 参数
});

// Jest 运行时
const reactDom = require('react-dom');  // 从 dist/node_modules/react-dom 加载
const react = require('react');         // 从 dist/node_modules/react 加载
// 然后把这两个作为参数传给 test-utils
```

---

关键要点：

1. **external 的作用**：告诉打包工具"这些依赖不要打包进来"
2. **运行时解析**：使用 require() 或 import 从外部加载这些依赖
3. **避免重复**：确保整个应用只有一份 react 和 react-dom
4. **减小体积**：打包产物更小

**验证方法：**

```bash
# 查看打包后文件大小
ls -lh dist/node_modules/react-dom/test-utils.js
# 应该很小（几 KB），而不是几 MB
```

</details>
