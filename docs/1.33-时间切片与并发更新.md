# 本次 Git 改动整理

## 第一部分:顶层鸟瞰

### 🎯 核心目标

本次改动让 React 从"必须一口气渲染完"升级为"可以边渲染边休息，有紧急任务来了还能暂停让路"的**并发渲染模式**。

### 📊 改动概览

**涉及文件：**
- `packages/react-reconciler/src/fiber.ts` - 新增调度状态字段
- `packages/react-reconciler/src/workLoop.ts` - 重构调度与渲染流程

**新增核心能力：**

1. **调度管理系统** - 智能决策任务优先级，支持调度复用和高优先级抢占
2. **时间切片机制** - 渲染过程可中断，每 5ms 让出主线程给浏览器
3. **可恢复渲染** - 中断后能从断点继续，不必重新开始
4. **优先级调度** - 同步任务（微任务）立即执行，并发任务（宏任务）分片执行

### 🔄 架构变化

#### 之前（同步渲染）
```
更新触发 → performSyncWorkOnRoot → 一口气渲染完 → commitRoot
                                    ↓（阻塞主线程）
                              浏览器无法响应用户操作
```

#### 现在（并发渲染）
```
更新触发 → ensureRootIsScheduled（调度中心）
            ↓
      判断优先级
      ├─ 高优先级（SyncLane）
      │   → 微任务 → performSyncWorkOnRoot → 同步渲染
      │
      └─ 低优先级（DefaultLane/IdleLane）
          → 宏任务 → performConcurrentWorkOnRoot
                      ↓
                  时间切片渲染（每 5ms 暂停一次）
                      ↓
                  可被高优先级任务打断
                      ↓
                  完成后 commitRoot
```

### 🎨 设计亮点

| 特性 | 实现方式 | 核心价值 |
|-----|---------|---------|
| **调度复用** | 同优先级更新复用已有调度，避免重复调度 | 提升性能，减少不必要的调度开销 |
| **优先级抢占** | 高优先级任务取消低优先级任务 | 保证用户交互及时响应 |
| **状态保留** | 中断时保留 `workInProgress` 断点 | 恢复执行时从断点继续，不重复劳动 |
| **连续执行** | 并发任务被中断后返回自身 continuation | Scheduler 自动继续调度，无需手动管理 |

### 💡 关键数据结构

```typescript
// 新增字段

  callbackNode: CallbackNode | null    // 当前调度任务句柄（用于取消）
  callbackPriority: Lane                // 当前调度优先级（用于比较）
}

// 新增状态机

const RootComplete = 2    // render 完成
```

### 🎬 典型场景

**场景：用户在滚动加载数据时突然点击按钮**

```
1. 滚动触发低优先级更新（DefaultLane）
   → 开始并发渲染，已渲染 10 个组件
   
2. 用户点击按钮（高优先级 SyncLane）
   → ensureRootIsScheduled 发现优先级变高
   → 取消低优先级任务
   → 立即同步渲染点击更新
   → commitRoot
   
3. 高优先级完成后
   → 重新调度低优先级更新
   → 继续渲染滚动数据（从头开始）
```

### 步骤 2:改造 workLoop，实现时间切片与并发渲染流程

**路径:** `packages/react-reconciler/src/workLoop.ts`

**修改内容:**

**(1) 新增导入与退出状态定义**
1. 从 `fiberLanes` 中新增导入 `laneToSchedulerPriority`，用于在调度时将 Lane 转换为 Scheduler 优先级
2. 新增 `unstable_shouldYield` 导入（来自 `scheduler` 包），用于在并发工作循环中判断当前时间切片是否用尽
3. 新增 render 阶段退出状态类型 `RootExitStatus`，以及两个状态常量：`RootIncomplete = 1`（render 被中断）、`RootComplete = 2`（render 执行完成）

**(2) `prepareFreshStack` 增加状态重置**
1. 初始化 workInProgress 之前，先重置 `root.finishedLane = NoLane`、`root.finishedWork = null`，避免上一次（可能被中断的）渲染残留的结果影响新的渲染

**(3) 改造 `ensureRootIsScheduled`，实现"调度复用 + 高优先级抢占"机制**
1. 读取 `root.callbackNode` 作为 `existingCallback`，记录当前已存在的调度任务
2. 没有待处理更新时（`maxPendingLane === NoLane`），取消已存在的调度任务（`unstable_cancelCallback`），并重置 `callbackNode`、`callbackPriority`，然后 return
3. 比较新的最高优先级 `curPriority` 与上次调度的 `prevPriority`（即 `root.callbackPriority`）：相同优先级的更新直接 return，复用已有调度，不重复调度
4. 优先级不同（代表更高优先级的更新插入），先取消之前已存在的调度任务
5. 同步优先级分支：`performSyncWorkOnRoot` 的绑定参数去掉了 `lane`（改为函数内部自行获取最高优先级 lane）
6. 实现其他优先级（并发）分支：通过 `laneToSchedulerPriority` 将 Lane 转换为 Scheduler 优先级，再调用 `scheduleCallback(schedulerPriority, performConcurrentWorkOnRoot.bind(null, root))` 用宏任务调度并发渲染，并保存返回的 `newCallbackNode`
7. 调度完成后，更新 `root.callbackNode` 和 `root.callbackPriority`，记录本次调度的任务节点和优先级

**(4) 新增 `performConcurrentWorkOnRoot`，并发更新的入口函数**
1. 调度开始前先执行 `flushPassiveEffects` 保证所有 useEffect 回调执行完毕——因为 useEffect 回调可能触发更高优先级的更新；如果执行后 `root.callbackNode` 发生了变化，说明有更高优先级任务插入，直接 return null 放弃本次任务
2. 获取当前最高优先级 `updateLane`，若为 `NoLane` 直接 return null
3. 计算 `needSync`：当 `updateLane === SyncLane` 或 Scheduler 传入 `didTimeout`（任务已过期）时，本次渲染退化为同步、不可中断
4. 调用 `renderRoot(root, updateLane, !needSync)` 执行 render 阶段，根据返回的退出状态分别处理：
   - `RootIncomplete`（中断）：若 `root.callbackNode` 已变化，代表有更高优先级任务插入，return null；否则返回 `performConcurrentWorkOnRoot.bind(null, root)`，利用 Scheduler 的"连续回调"机制在下一个时间切片继续执行
   - `RootComplete`（完成）：设置 `root.finishedWork`、`root.finishedLane`，重置 `wipRootRenderLane`，进入 `commitRoot` 提交阶段
5. render 结束后调用 `ensureRootIsScheduled(root)` 重新调度剩余更新

**(5) 改造 `performSyncWorkOnRoot`，render 逻辑抽离**
1. 函数签名移除 `lane` 参数，改为内部通过 `getHighestPriorityLane(root.pendingLanes)` 获取
2. 原本内联的 render 阶段逻辑（初始化、workLoop 循环、错误处理）抽离为公共的 `renderRoot` 函数，此处改为调用 `renderRoot(root, nextLane, false)`（同步、不可中断）
3. 根据返回的退出状态处理：`RootComplete` 时设置 `finishedWork`、`finishedLane` 并进入 `commitRoot`；其他状态在 DEV 环境下报错"还未实现的同步更新结束状态"

**(6) 新增 `renderRoot`，同步/并发共用的 render 阶段入口**
1. 接收 `shouldTimeSlice` 参数，决定走时间切片（并发）还是同步流程
2. 仅当 `wipRootRenderLane !== lane` 时才调用 `prepareFreshStack` 初始化——中断后恢复执行同一优先级的渲染时，复用已有的 workInProgress，从中断处继续，这是时间切片"可恢复"的关键
3. 工作循环根据 `shouldTimeSlice` 分流：`workLoopConcurrent()`（可中断）或 `workLoopSync()`（不可中断）
4. 循环结束后根据 `workInProgress` 状态返回退出状态：
   - 时间切片模式下 `workInProgress !== null`，说明被中断，返回 `RootIncomplete`
   - 同步模式下 `workInProgress` 不为 null 属于异常，DEV 环境下报错
   - 其余情况返回 `RootComplete`
5. 渲染完成后不再直接调用 `commitRoot`，commit 时机交由调用方（`performSyncWorkOnRoot` / `performConcurrentWorkOnRoot`）根据退出状态决定

**(7) 工作循环拆分为同步/并发两个版本**
1. 原 `workLoop` 重命名为 `workLoopSync`，逻辑不变：循环执行 `performUnitOfWork` 直到 `workInProgress` 为 null
2. 新增 `workLoopConcurrent`，循环条件额外加入 `!unstable_shouldYield`：当 Scheduler 判断当前时间切片用尽时跳出循环，让出主线程，实现时间切片

## 第三部分:主要知识点

### 本次改动的核心内容

#### 📦 能力 1：调度管理系统

##### 之前（简单粗暴）
```
有更新 → 直接执行 performSyncWorkOnRoot → 一口气渲染完
```

##### 现在（智能调度）
```
有更新 
  ↓
ensureRootIsScheduled（调度中心）
  ↓
判断：这个更新重要吗？
  ├─ 很重要（SyncLane，比如用户点击）
  │   → 微任务调度，立即执行 performSyncWorkOnRoot
  │
  └─ 不太急（DefaultLane，比如数据加载）
      → 宏任务调度，稍后执行 performConcurrentWorkOnRoot
```

##### 新增的字段作用
```typescript
FiberRootNode {
  callbackNode: 当前正在调度的任务ID
  callbackPriority: 当前任务的优先级
}
```

**举例说明：**
```
1. 用户触发了一个低优先级更新（滚动加载数据）
   root.callbackNode = Task#123（任务ID）
   root.callbackPriority = DefaultLane

2. 突然用户点击按钮（高优先级）
   ensureRootIsScheduled 发现：
   - curPriority = SyncLane（新的高优先级）
   - prevPriority = DefaultLane（旧的低优先级）
   - 不一样！需要取消旧任务！
   
   操作：
   unstable_cancelCallback(root.callbackNode) // 取消 Task#123
   安排新的高优先级任务
```

#### ⏱️ 能力 2：时间切片（Time Slicing）

##### 什么是时间切片？
就像吃饭时有人找你聊天，你可以：
- **旧方式**：一口气把饭吃完再说话（阻塞）
- **新方式**：吃一口饭，回一句话，再吃一口（切片）

##### 工作循环对比

**同步循环（workLoopSync）**
```typescript
function workLoopSync() {
  while (workInProgress !== null) {
    performUnitOfWork(workInProgress); // 一直干活，不休息
  }
}
```
**特点**：必须全部完成才停下

**并发循环（workLoopConcurrent）**
```typescript
function workLoopConcurrent() {
  while (workInProgress !== null && !unstable_shouldYield()) {
    performUnitOfWork(workInProgress); // 干一会就问：要让路吗？
  }
}
```
**特点**：
- `unstable_shouldYield()`：Scheduler 说"这 5ms 用完了，该让给浏览器了"
- 返回 true 时，跳出循环，让浏览器处理用户输入/动画等
- 稍后再继续渲染

#### 🔄 能力 3：可恢复渲染（Resumable Render）

##### 关键机制：renderRoot 函数

```typescript
function renderRoot(root, lane, shouldTimeSlice) {
  // 🔑 关键判断
  if (wipRootRenderLane !== lane) {
    // 不是同一个任务，需要重新开始
    prepareFreshStack(root, lane);
  }
  // 如果是同一个任务，不初始化，直接从 workInProgress 继续！
  
  do {
    shouldTimeSlice ? workLoopConcurrent() : workLoopSync();
  } while (true);
  
  // 返回状态：完成了？还是被中断了？
  if (shouldTimeSlice && workInProgress !== null) {
    return RootIncomplete; // 还没完成，下次继续
  }
  return RootComplete; // 完成了
}
```

##### 实际流程演示

```
时间切片 1 (0-5ms):
  渲染 ComponentA ✅
  渲染 ComponentB ✅
  渲染 ComponentC（一半）⏸️
  unstable_shouldYield() 返回 true
  → 返回 RootIncomplete
  → workInProgress 指向 ComponentC（记住断点）

时间切片 2 (5-10ms):
  浏览器处理用户输入
  
时间切片 3 (10-15ms):
  Scheduler 继续调用 performConcurrentWorkOnRoot
  → renderRoot 发现 wipRootRenderLane 没变
  → 不初始化，从 workInProgress（ComponentC）继续！
  渲染 ComponentC（剩余部分）✅
  渲染 ComponentD ✅
  → 返回 RootComplete
  → commitRoot（提交到 DOM）
```

#### 🎬 能力 4：高优先级打断

##### 完整场景

```
初始状态：
  用户滚动页面 → 触发低优先级更新（渲染长列表）
  root.callbackNode = Task#100
  root.callbackPriority = DefaultLane

执行中：
  performConcurrentWorkOnRoot(Task#100)
    ↓
  renderRoot(root, DefaultLane, true) // 开始并发渲染
    ↓
  workLoopConcurrent() 执行中...
  已经渲染了 10 个组件

突发情况：
  用户点击按钮！（高优先级）
    ↓
  scheduleUpdateOnFiber(fiber, SyncLane)
    ↓
  ensureRootIsScheduled(root)
    发现：curPriority (SyncLane) > prevPriority (DefaultLane)
    操作：
      1. unstable_cancelCallback(Task#100) // 取消低优先级任务
      2. scheduleSyncCallback(performSyncWorkOnRoot) // 安排同步任务
      3. root.callbackNode = null（同步任务不走 Scheduler）
      4. root.callbackPriority = SyncLane

立即执行：
  performSyncWorkOnRoot()
    ↓
  renderRoot(root, SyncLane, false) // 同步渲染
    发现：wipRootRenderLane (DefaultLane) !== SyncLane
    操作：prepareFreshStack(root, SyncLane) // 重新开始
    ↓
  workLoopSync() // 一口气渲染完高优先级更新
    ↓
  commitRoot() // 提交
  
后续：
  ensureRootIsScheduled(root) 
    发现：root.pendingLanes 里还有低优先级更新（长列表）
    重新调度 → 继续渲染长列表（从头开始）
```

### 关键数据结构变化

#### FiberRootNode 新增字段
```typescript
class FiberRootNode {
  // 新增 ↓
  callbackNode: CallbackNode | null;    // Scheduler 返回的任务句柄
  callbackPriority: Lane;                // 当前任务优先级
  
  // 原有 ↓
  pendingLanes: Lanes;                   // 所有待处理更新的优先级集合
  finishedWork: FiberNode | null;        // 渲染完成的 Fiber 树
  finishedLane: Lane;                    // 已完成的优先级
}
```

#### 状态机
```typescript
type RootExitStatus = number;
const RootIncomplete = 1;  // render 被中断（时间切片用尽或出错）
const RootComplete = 2;    // render 完成（整棵树遍历结束）
```

### 核心函数职责

#### 1. ensureRootIsScheduled（调度中心）
```
输入：FiberRootNode
职责：
  1. 检查是否有更新
  2. 比较新旧优先级
  3. 决定用什么方式调度（微任务/宏任务）
  4. 取消过时的任务
  5. 记录新任务信息
输出：调度任务已安排
```

#### 2. performConcurrentWorkOnRoot（并发工作入口）
```
输入：FiberRootNode, didTimeout（是否超时）
职责：
  1. 清空副作用（flushPassiveEffects）
  2. 检查是否被高优先级打断
  3. 调用 renderRoot 渲染
  4. 根据返回状态决定：
     - 中断 → 返回自己（继续调度）
     - 完成 → commitRoot（提交）
输出：null 或 continuation 函数
```

#### 3. performSyncWorkOnRoot（同步工作入口）
```
输入：FiberRootNode
职责：
  1. 调用 renderRoot(false) 同步渲染
  2. 完成后立即 commitRoot
输出：void
```

#### 4. renderRoot（渲染核心）
```
输入：FiberRootNode, lane, shouldTimeSlice
职责：
  1. 判断是否需要重新初始化
  2. 选择工作循环（同步/并发）
  3. 返回退出状态
输出：RootExitStatus
```

### 设计精髓

#### 1. 调度复用
同优先级的连续更新不会重复调度：
```typescript
if (curPriority === prevPriority) return; // 复用已有调度
```

#### 2. 状态保留
中断时保留 workInProgress，恢复时从断点继续：
```typescript
if (wipRootRenderLane !== lane) {
  prepareFreshStack(root, lane); // 只在切换任务时重置
}
```

#### 3. 优先级抢占
高优先级任务会取消低优先级任务：
```typescript
if (existingCallback !== null) {
  unstable_cancelCallback(existingCallback);
}
```

#### 4. 连续执行
并发任务被中断后返回自己，Scheduler 会继续调度：
```typescript
if (exitStatus === RootIncomplete) {
  return performConcurrentWorkOnRoot.bind(null, root);
}
```

---

### 理解要点

#### 1. 调度 ≠ 执行
- **调度**：决定什么时候做什么任务（ensureRootIsScheduled）
- **执行**：真正渲染组件（renderRoot）

#### 2. 同步 vs 并发
- **同步**：一次性完成，不可中断（用户交互）
- **并发**：分片执行，可中断（数据加载）

#### 3. 中断 ≠ 取消
- **中断**：暂停，稍后继续（时间切片）
- **取消**：彻底放弃，重新开始（高优先级打断）

#### 4. Lane 优先级决定调度方式
- **SyncLane** → 微任务 → performSyncWorkOnRoot
- **其他 Lane** → 宏任务 → performConcurrentWorkOnRoot

---

### 三层抽象架构

```
第 1 层：调度层（什么时候做）
  ensureRootIsScheduled → 决定用微任务还是宏任务

第 2 层：执行层（怎么做）
  performSyncWorkOnRoot（同步，一口气做完）
  performConcurrentWorkOnRoot（并发，分片做）

第 3 层：渲染层（做什么）
  renderRoot → 调用 workLoop 遍历 Fiber 树
    ├─ workLoopSync（不可中断）
    └─ workLoopConcurrent（可中断）
```

**关键理解：**
- **同步更新**：调度层（微任务）→ 执行层（performSyncWorkOnRoot）→ 渲染层（workLoopSync）
- **并发更新**：调度层（宏任务）→ 执行层（performConcurrentWorkOnRoot）→ 渲染层（workLoopConcurrent）→ 可能中断 → Scheduler 继续调度 → 恢复执行
