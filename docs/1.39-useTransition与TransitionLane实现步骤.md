## 第三部分:主要知识点

### 本次改动的核心内容

#### 做了什么事

本次改动是**实现 `useTransition` Hook，并将 transition 更新接入 Lane 优先级模型**，让「切换 UI 触发的更新」可以被标记为低优先级，从而不阻塞用户交互。

结合课程截图，用源码术语翻译 `useTransition` 的行为：

- **切换 UI → 触发 update**：用户在 `startTransition` 回调里调用 `setState`，本质仍是触发一次更新
- **先展示旧 UI，加载完再展示新 UI**：「切换到新 UI」这一步被标记为**低优先级 update**，可以被更高优先级的交互打断

具体涉及三个实现层次（对应课程截图中的三个要点）：

1. **实现基础 Hook 工作流程** — 在 `Dispatcher` / `fiberHooks` 中注册 `useTransition`，完成 mount / update 双路径
2. **实现 Transition 优先级** — 通过 `currentBatchConfig` + `TransitionLane` + `requestUpdateLanes` 让 transition 上下文内的 update 获得低优先级
3. **`useTransition` 的实现细节** — `useState` 管理 `isPending`，独立 hook 存储 `startTransition`，并在 `startTransition` 内完成「改优先级 → 执行 callback → 还原优先级」

---

### 为什么要改动

#### 1. 并发场景下，并非所有更新都需要立即响应

普通 `setState` 会走当前 Scheduler 上下文对应的 Lane（如点击事件 → `SyncLane`）。但像 Tab 切换、列表筛选这类「可以稍后再渲染」的 UI 更新，如果仍用高优先级，会阻塞更紧急的交互。

`useTransition` 的价值就是：**把这类更新主动降级**，让用户先继续操作，新 UI 在后台渲染。

#### 2. 优先级要能影响 update，才能影响更新行为

与 1.32 文档一致，课程的核心结论是：

> **只要优先级能影响 update，就能影响更新**

本次在 `requestUpdateLanes()` 最前面增加 transition 判断，就是在「产生 update 时」注入优先级信息，而不是在调度阶段才临时处理。

#### 3. 需要一个全局上下文标记「当前是否在 transition 中」

`startTransition` 是一个普通函数调用，callback 内部的 `setState` 需要通过某种方式知道自己处于 transition 上下文。因此引入 `currentBatchConfig.transition` 作为全局标记，在 callback 执行期间临时写入，执行完毕后还原。

---

### 实现了什么功能

#### 功能 1：`useTransition` 的基础 Hook 结构

`useTransition` 在内部占用 **两个 hook 节点**（对应课程截图左侧的 `useState` + `hook`）：

| Hook 节点 | 存储内容 | 作用 |
|----------|---------|------|
| 第 1 个 hook | `useState(false)` 的 state / queue | 维护 `isPending` 状态 |
| 第 2 个 hook | `startTransition` 函数（存在 `memoizedState`） | 返回给组件的 `startTransition` |

**mount 时：**

```typescript
function mountTransition() {
  const [isPending, setPending] = mountState(false);  // hook 1
  const hook = mountWorkInProgressHook();              // hook 2
  const start = startTransition.bind(null, setPending);
  hook.memoizedState = start;
  return [isPending, start];
}
```

**update 时：**

```typescript
function updateTransition() {
  const [isPending] = updateState();       // 消费 hook 1
  const hook = updateWorkInProgressHook(); // 读取 hook 2
  const start = hook.memoizedState;
  return [isPending, start];
}
```

`startTransition` 函数通过 `bind` 闭包持有 `setPending`，因此组件每次 render 拿到的 `start` 函数始终能操作同一个 pending 状态。

---

#### 功能 2：`startTransition` 的执行流程

对应课程截图右侧 `startTransition` 的五步流程：

```
setPending(true)          ← 标记 transition 开始（正常优先级）
    ↓
改变优先级               ← currentBatchConfig.transition = 1
    ↓
callback()               ← 回调内的 setState 获得 TransitionLane
    ↓
setPending(false)        ← 标记 transition 结束
    ↓
还原优先级               ← currentBatchConfig.transition = prevTransition
```

**源码实现：**

```typescript
function startTransition(setPending, callback) {
  setPending(true);                                    // ① pending 指示
  const prevTransition = currentBatchConfig.transition;

  currentBatchConfig.transition = 1;                   // ② 改变优先级

  callback();                                          // ③ 执行回调

  setPending(false);                                   // ④ 清除 pending
  currentBatchConfig.transition = prevTransition;      // ⑤ 还原优先级
}
```

**两个 setPending 的优先级差异：**

| 调用 | transition 上下文 | 获得的 Lane | 说明 |
|------|------------------|------------|------|
| `setPending(true)` | `null`（尚未设置） | 当前 Scheduler 上下文对应的 Lane | pending 指示应尽快出现 |
| callback 内 setState | `1` | `TransitionLane` | 真正的 UI 切换更新，低优先级 |
| `setPending(false)` | 仍为 `1` | `TransitionLane` | pending 清除也走 transition 优先级 |

---

#### 功能 3：Transition 优先级接入 Lane 模型

**新增 `TransitionLane` 及其在 Lane 体系中的位置：**

| Lane | 二进制 | 优先级顺序 | Scheduler 映射 |
|------|--------|-----------|---------------|
| `SyncLane` | `0b00001` | 最高 | `ImmediatePriority` |
| `InputContinuousLane` | `0b00010` | ↓ | `UserBlockingPriority` |
| `DefaultLane` | `0b00100` | ↓ | `NormalPriority` |
| **`TransitionLane`** | **`0b01000`** | **↓** | **`LowPriority`** |
| `IdleLane` | `0b10000` | 最低 | `IdlePriority` |

**`requestUpdateLanes` 的判断逻辑：**

```typescript
export function requestUpdateLanes() {
  const isTransition = currentBatchConfig.transition !== null;
  if (isTransition) {
    return TransitionLane;  // transition 上下文内，强制低优先级
  }
  // 否则走 Scheduler 优先级转换
  const currentSchedulerPriority = unstable_getCurrentPriorityLevel();
  return schedulerPriorityToLane(currentSchedulerPriority);
}
```

**`currentBatchConfig` 的单例访问：**

- `react/index.ts` 创建单例并挂到 `__SECRET_INTERNALS_DO_NOT_USE_OR_YOU_WILL_BE_FIRED`
- `fiberLanes.ts` / `fiberHooks.ts` 通过 `shared/internals` 解构读取，与 `currentDispatcher` 保持同一访问路径，避免多实例

### 完整工作流程

结合本次改动，一次 `useTransition` 调用的完整链路如下：

```
组件调用 startTransition(() => setCount(n))
  ↓
startTransition: setPending(true)
  → requestUpdateLanes() → 正常 Lane（如 DefaultLane）
  → scheduleUpdateOnFiber → isPending = true
  ↓
startTransition: currentBatchConfig.transition = 1
  ↓
callback 内 setCount(n)
  → requestUpdateLanes() → TransitionLane（低优先级）
  → scheduleUpdateOnFiber → UI 更新进入低优先级队列
  ↓
startTransition: setPending(false)
  → requestUpdateLanes() → TransitionLane
  → isPending = false
  ↓
startTransition: currentBatchConfig.transition = prevTransition
  ↓
ensureRootIsScheduled(root)
  → getHighestPriorityLane(pendingLanes)
  → 若同时存在 SyncLane 和 TransitionLane，SyncLane 优先
  → TransitionLane → laneToSchedulerPriority → LowPriority
  → scheduleCallback(LowPriority, performConcurrentWorkOnRoot)
  ↓
Scheduler 以低优先级执行 transition 更新
  → 高优先级交互可打断，实现「先展示旧 UI」
```

---

### 辅助改动说明

#### `mountState` 补充 `baseState` 初始化

`useTransition` 内部复用 `mountState(false)` 管理 pending 状态。`updateState` 计算新 state 时以 `hook.baseState` 为起点，若 mount 时不初始化，首次 `setPending(true/false)` 会从 `null` 起算，导致 state 计算错误。因此需要在 `mountState` 中同步设置 `hook.baseState = memoizedState`。

---

### 核心价值

这次改动实现了课程中 `useTransition` 的三层目标：

1. **Hook 层** — 对外暴露 `[isPending, startTransition]`，内部用两个 hook 节点分工
2. **优先级层** — 通过 `currentBatchConfig` + `TransitionLane` 让 transition 更新可被识别、被降级
3. **调度层** — `TransitionLane` 映射到 `LowPriority`，经 Scheduler 宏任务调度，可被更高优先级更新打断

这是并发渲染中「可中断的低优先级更新」的基础设施，为后续实现「高优先级 update 打断低优先级 render」提供了前提条件。
