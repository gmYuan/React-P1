**路径:** `packages/react-reconciler/src/fiberLanes.ts`

**修改内容:**
1. 新增 `Lane` / `Lanes` 类型，分别表示单个优先级与优先级集合
2. 新增常量：`NoLane`、`NoLanes`、`SyncLane`
3. 新增 `mergeLanes`，通过按位或合并优先级
4. 新增 `requestUpdateLanes`，当前先固定返回 `SyncLane`，为后续接 Scheduler 预留扩展位

```diff

+
+ export const NoLane = 0b0000;
+ export const NoLanes = 0b0000;
+ export const SyncLane = 0b0001;

+ export function mergeLanes(laneA: Lane, laneB: Lane): Lanes {

+ }
```

## 第四部分:个人 Q&A

### 1. 这批改动文件的主题是什么？为什么要改这些文件？

这批改动的主题是：给更新系统加上「优先级标签（Lane）」，并把这个标签从「更新产生」一路传到「根节点记录」。

从流程上看，就是围绕 `update -> schedule -> render -> commit` 这条链路，先把 lane 的基础能力接入进去。当前阶段重点不是完整调度策略，而是先把“优先级信息可以被产生、携带、传递、记录”这条数据通路打通。

各文件改动目的如下：

1. `packages/react-reconciler/src/fiberLanes.ts`
   - 定义 lane 体系本身（`Lane`、`Lanes`、`NoLane`、`NoLanes`、`SyncLane`）
   - 提供 `mergeLanes`（合并优先级）和 `requestUpdateLanes`（分配本次更新优先级）
   - 通俗理解：先约定“优先级这门语言”，后面大家才知道怎么交流

2. `packages/react-reconciler/src/updateQueue.ts`
   - 给每个 update 增加 `lane` 字段
   - `createUpdate` 接收并写入 lane
   - 通俗理解：每条更新都带上“优先级身份证”，后续才能按优先级决定先处理谁

3. `packages/react-reconciler/src/fiberReconciler.ts`
   - 在容器更新入口 `updateContainer` 中申请 lane
   - 创建 update 和触发调度时都传入 lane
   - 通俗理解：从应用更新主入口开始，保证更新不是“裸数据”

4. `packages/react-reconciler/src/fiberHooks.ts`
   - 在 Hook 更新入口 `dispatchSetState` 中同样申请 lane 并向下传递
   - 通俗理解：`setState` 这条路也要统一接入优先级，不然系统会出现“部分更新有优先级、部分没有”的不一致

5. `packages/react-reconciler/src/workLoop.ts`
   - 调整 `scheduleUpdateOnFiber` 签名，接收 lane
   - 新增 `markRootUpdated`，把 lane 合并到 `root.pendingLanes`
   - 通俗理解：调度阶段把这次更新登记到 root 的“待办优先级清单”里，后续才有基础做“选择某个 lane 渲染”

6. `packages/react-reconciler/src/fiber.ts`
   - 给 `FiberRootNode` 增加 `pendingLanes` 和 `finishedLane`
   - 初始化为 `NoLanes` / `NoLane`
   - 通俗理解：root 需要一个“账本”，分别记录“还有哪些优先级没处理”和“这轮处理的是哪个优先级”

总结起来就是一条完整链路：

**定义 lane -> update 携带 lane -> 调度接收 lane -> root 记录 lane**

少任何一环，lane 模型都无法真正落地，所以这些文件需要一起改。
