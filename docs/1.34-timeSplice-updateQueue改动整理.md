## 第三部分:主要知识点

### 本次改动的核心目标

**让 React 在时间切片（并发渲染）过程中，能够"跳过低优先级 update"，并在后续渲染时正确恢复和计算被跳过的 update。**

---

### 为什么需要这个改动？

#### 问题背景

上一次 commit（1.33 时间切片与并发更新）实现了：
- 时间切片：render 可以被中断
- 并发调度：高优先级任务可以打断低优先级任务

但有个**致命问题**：

```
场景：
1. 用户触发低优先级更新 u0 (DefaultLane)
2. 正在渲染时，用户又触发高优先级更新 u1 (SyncLane)  
3. 高优先级打断，立即渲染 u1
4. u1 渲染完成后，再回来渲染 u0

问题出在哪？
当重新渲染 u0 时，按照之前的逻辑：
- processUpdateQueue 会把 u0 和 u1 都计算一遍
- 但 u1 已经在高优先级渲染时被消费过了！
- 这会导致 state 计算错误
```

#### 实际案例

```javascript
// 有三个 update
u0: { action: num => num + 1, lane: DefaultLane }   // 低优先级
u1: { action: 3, lane: SyncLane }                    // 高优先级  
u2: { action: num => num + 10, lane: DefaultLane }   // 低优先级

// 初始 state = 0

// 第一次 render (updateLane = DefaultLane)
// 如果只考虑优先级: 结果为 11 (0 → 1 → 11，跳过 u1)
// 如果考虑连续性: 结果应为 13 (0 → 1 → 3 → 13)
```

**问题的本质：**
- 第一次 render 时，u0 和 u2 优先级都够，但 u1 优先级不够
- 如果跳过 u1，计算 u0 → u2，得到 11
- 但这样破坏了 update 的连续性！
- 因为 u1 可能在后续的高优先级渲染中被执行，然后再回来执行 u2
- 最终结果应该是 13 (0 → 1 → 3 → 13)

---

### 解决方案的核心思路

1. **跳过优先级不够的 update**
2. **保存被跳过的 update 到 baseQueue**  
3. **保证 update 的连续性**：第一个被跳过的 update 之后的所有 update（即使优先级够）也要保存到 baseQueue
4. **在下次渲染时，从 baseQueue 恢复并重新计算**

---

### 具体实现机制

#### 1. Hook 新增字段

```typescript
interface Hook {
  memoizedState: any;      // 最终计算的 state
  updateQueue: unknown;
  next: Hook | null;
  
  // 新增 ↓
  baseState: any;          // 本次更新参与计算的初始 state
  baseQueue: Update<any> | null;  // 被跳过的 update 链表
}
```

**字段含义：**
- `baseState`：记录"最后一个没被跳过的 update 计算后的结果"
- `baseQueue`：保存"第一个被跳过的 update 及其后面所有 update"

#### 2. processUpdateQueue 处理逻辑

**之前的逻辑：**
```typescript
// 简化版
遍历 update 链表 {
  if (updateLane === renderLane) {
    baseState = 计算(baseState, update.action)
  } else {
    报错 // 不应该进入这个分支
  }
}
return { memoizedState: baseState }
```

**现在的逻辑：**
```typescript
let newState = baseState        // 本次计算的最新 state
let newBaseState = baseState    // 记录 baseState
let newBaseQueueFirst = null    // 被跳过的 update 链表头
let newBaseQueueLast = null     // 被跳过的 update 链表尾

遍历 update 链表 {
  if (!isSubsetOfLanes(renderLane, updateLane)) {
    // 优先级不够，跳过
    clone = 克隆(update)
    
    if (newBaseQueueLast === null) {
      // 这是第一个被跳过的
      newBaseQueueFirst = clone
      newBaseQueueLast = clone
      newBaseState = newState  // 记录跳过前的 state
    } else {
      // 添加到链表末尾
      newBaseQueueLast.next = clone
      newBaseQueueLast = clone
    }
  } else {
    // 优先级够
    if (newBaseQueueLast !== null) {
      // 前面有被跳过的，这个也要保存（保证连续性）
      clone = 克隆(update, NoLane)  // 优先级降为 NoLane
      newBaseQueueLast.next = clone
      newBaseQueueLast = clone
    }
    
    // 正常计算
    newState = 计算(newState, update.action)
  }
}

if (newBaseQueueLast === null) {
  // 没有被跳过的 update
  newBaseState = newState
} else {
  // 有被跳过的，形成环状链表
  newBaseQueueLast.next = newBaseQueueFirst
}

return {
  memoizedState: newState,
  baseState: newBaseState,
  baseQueue: newBaseQueueFirst
}
```

#### 3. updateState 的 baseQueue 合并机制

**关键：合并 baseQueue 和 pending**

```typescript
const baseState = hook.baseState
const current = currentHook as Hook
let baseQueue = current.baseQueue  // 从 current 读取上次的 baseQueue

if (pending !== null) {
  if (baseQueue !== null) {
    // 合并两个环状链表
    // baseQueue: b2 -> b0 -> b1 -> b2
    // pending:   p2 -> p0 -> p1 -> p2
    // 合并后:    b2 -> p0 -> p1 -> p2 -> b0 -> b1 -> b2
    
    const baseFirst = baseQueue.next
    const pendingFirst = pending.next
    baseQueue.next = pendingFirst
    pending.next = baseFirst
  }
  baseQueue = pending
  current.baseQueue = pending  // 保存到 current
  
  // 调用新版 processUpdateQueue
  const { memoizedState, baseQueue: newBaseQueue, baseState: newBaseState } =
    processUpdateQueue(baseState, baseQueue, renderLane)
  
  hook.memoizedState = memoizedState
  hook.baseState = newBaseState
  hook.baseQueue = newBaseQueue
}
```

### 完整流程演示

以前面的案例为例：

```javascript
// 初始状态
state = 0

// 三个 update
u0: { action: num => num + 1, lane: DefaultLane }
u1: { action: 3, lane: SyncLane }
u2: { action: num => num + 10, lane: DefaultLane }
```

#### 第一次 render (updateLane = DefaultLane)

```
处理 u0:
  - 优先级够 (DefaultLane)
  - newBaseQueueLast === null (还没有被跳过的)
  - 正常计算: newState = 0 + 1 = 1

处理 u1:
  - 优先级不够 (SyncLane > DefaultLane)
  - 这是第一个被跳过的!
  - newBaseState = 1 (记录跳过前的 state)
  - newBaseQueueFirst = u1
  - newBaseQueueLast = u1

处理 u2:
  - 优先级够 (DefaultLane)
  - 但是前面有被跳过的 (newBaseQueueLast !== null)
  - 也要保存到 baseQueue，优先级降为 NoLane
  - newBaseQueueLast.next = u2(NoLane)
  - 同时也要计算: newState = 1 + 10 = 11

第一次 render 结果:
  memoizedState = 11
  baseState = 1
  baseQueue = u1 -> u2(NoLane) -> u1 (环状)
```

#### 第二次 render (updateLane = SyncLane，高优先级插入)

```
从 baseQueue 恢复: u1 -> u2(NoLane)
从 baseState 开始计算: state = 1

处理 u1:
  - 优先级够 (SyncLane)
  - 正常计算: newState = 3

处理 u2:
  - 优先级是 NoLane（被降级了）
  - NoLane 代表"必须参与计算"
  - 正常计算: newState = 3 + 10 = 13

第二次 render 结果:
  memoizedState = 13
  baseState = 13
  baseQueue = null (全部处理完了)
```

### 关键设计点解析

#### 1. 为什么保存到 current.baseQueue？

考虑将 update 保存在 current 中，只要不进入 commit 阶段，current 与 wip 不会互换，所以即使多次执行 render 阶段，只要不进入 commit 阶段，都能从 current 中恢复数据。

**原因：**
- render 可能被中断多次
- 只要不进入 commit，current 和 wip 不会互换
- baseQueue 保存在 current 中就能一直保留
- 每次重新渲染时都能从 current 恢复

#### 2. 为什么优先级够的 update 也要保存到 baseQueue？

**保证 update 的连续性和顺序。**

如果不保存：
```
第一次: 处理 u0, 跳过 u1, 处理 u2 → state = 11
第二次: 处理 u1 → state = 3
结果错误！u2 丢失了
```

如果保存：
```
第一次: 处理 u0, 跳过 u1, u2 也保存 → state = 11 (临时)
第二次: 从 baseState=1 开始, 处理 u1 → u2 → state = 13
结果正确！
```

#### 3. 为什么要降级为 NoLane？

```typescript
// 参与计算但保存在 baseQueue 中的 update
clone = createUpdate(pending.action, NoLane)
```

**原因：**
- 这些 update 已经参与过一次计算了（虽然结果是临时的）
- 下次渲染时必须执行，不能再被跳过
- NoLane 代表"最高优先级，必须处理"

#### 4. baseState vs memoizedState 的区别

**baseState：**
- 本次更新参与计算的**初始** state
- 是"最后一个没被跳过的 update 计算后的结果"

**memoizedState：**
- 上次更新计算的**最终** state
- 是考虑优先级情况下计算的结果

**示例：**
```
第一次 render:
  baseState = 0 (初始)
  处理 u0 → 中间 state = 1
  跳过 u1
  处理 u2 → memoizedState = 11
  保存 newBaseState = 1 (最后没被跳过的结果)

第二次 render:
  baseState = 1 (从上次的 newBaseState 开始)
  处理 u1 → 中间 state = 3
  处理 u2 → memoizedState = 13
  newBaseState = 13 (全部处理完)
```

### 本次改动的价值

#### 解决的核心问题

**时间切片和优先级调度场景下，update 的连续性和正确性。**

#### 实现的关键能力

1. **跳过低优先级 update**：render 阶段可以按优先级选择性处理 update
2. **保持 update 连续性**：即使跳过某些 update，最终计算结果仍然正确
3. **支持多次中断恢复**：通过 current.baseQueue 机制，可以在多次 render 中断后恢复
4. **优先级调度的正确性**：高优先级任务插入后，低优先级任务能正确恢复并继续

#### 在 React 并发架构中的位置

```
并发更新的完整链路：
1. 时间切片机制（1.33 完成）→ render 可以被中断
2. 优先级调度（1.33 完成）→ 高优先级任务可以打断低优先级任务
3. update 跳过与恢复（本次完成）→ 保证跳过后能正确恢复
4. Suspense 与并发特性（待完成）→ 基于以上能力实现更复杂的特性
```

这个改动是实现 React 并发特性的**关键基础**，确保了在复杂的优先级调度场景下，state 更新的正确性。
