### 步骤 1:在 updateContainer 中实现 mount 阶段的同步更新优先级

**路径:** `packages/react-reconciler/src/fiberReconciler.ts`

**修改内容:**
1. 新增 Scheduler 优先级 API 导入（`unstable_runWithPriority`、`unstable_ImmediatePriority`），用于在 mount 阶段设置同步优先级上下文
2. 改造 `updateContainer()` 的更新调度逻辑：将 `hostRootFiber` 获取、`requestUpdateLanes()`、`enqueueUpdate()`、`scheduleUpdateOnFiber()` 整体包裹在 `unstable_runWithPriority(unstable_ImmediatePriority, ...)` 中，使首屏更新在 `ImmediatePriority` 上下文下执行
3. 新增注释说明：React 官方默认首屏采用同步渲染，本次通过上述方式实现该策略

**关键代码:**

```diff
// packages/react-reconciler/src/fiberReconciler.ts
 import { requestUpdateLanes } from './fiberLanes';
+import { unstable_runWithPriority } from 'scheduler';
+import { unstable_ImmediatePriority } from 'scheduler';
...

   element: ReactElementType | null,
   root: FiberRootNode
 ) {
-  const hostRootFiber = root.current;
-  const renderLane = requestUpdateLanes();
-  const update = createUpdate<ReactElementType | null>(element, renderLane);
-  enqueueUpdate(
-    hostRootFiber.updateQueue as UpdateQueue<ReactElementType | null>,
-    update
-  );
-  scheduleUpdateOnFiber(hostRootFiber, renderLane);
+  // 这里官方默认首屏是 同步渲染的，如果想要实现的话,可以使用如下方式

+    const hostRootFiber = root.current;
+    const renderLane = requestUpdateLanes();

+      hostRootFiber.updateQueue as UpdateQueue<ReactElementType | null>,

+    scheduleUpdateOnFiber(hostRootFiber, renderLane);
+  });
+

```

## 第三部分:主要知识点

### 本次改动的核心内容

#### 做了什么事

本次改动是在 `updateContainer` 中**标注 mount 阶段（首屏渲染）应默认走同步更新**，并给出通过 Scheduler 优先级上下文实现该策略的代码思路。这是实现 `useTransition` 的前置铺垫——先确立「默认同步、按需并发」的并发策略，后续再在并发特性（如 `useTransition`）中主动触发低优先级更新。

---

### 为什么要改动

#### 1. 并发策略需要从「默认并发」调整为「默认同步」

课程指出，当前项目已具备并发更新能力，但并发策略需要调整为：

| 策略 | 说明 |
|------|------|
| **默认** | 启用**同步更新** |
| **使用并发特性后** | 那次更新启用**并发更新** |

其中，「默认启用同步更新」需要修改的关键位置是：**mount 时的更新优先级**——即首屏 `updateContainer` 触发的第一次更新，不应走低优先级并发路径，而应以同步方式尽快完成首屏渲染。

#### 2. 与 `requestUpdateLanes` 的优先级链路衔接

在 1.32 中已建立 Scheduler 优先级 → Lane 的转换机制：`requestUpdateLanes()` 会从当前 Scheduler 上下文读取优先级并转换为 Lane。因此，若要让 mount 更新获得 `SyncLane`，需要在 `updateContainer` 执行期间将 Scheduler 上下文设为 `ImmediatePriority`——这正是注释中 `unstable_runWithPriority(unstable_ImmediatePriority, ...)` 的作用。

---

### useTransition 的作用

#### 传统「过渡」体验的问题

从 UI **a** 切换到 UI **b**，通常有 3 个状态：

1. **初始状态**：展示 UI a
2. **过渡开始**：展示「过渡中」效果（如 loading）
3. **过渡完成**：切换到 UI b

传统 loading 过渡的缺陷：

- 过渡时间很短时，loading 效果会显得**生硬**
- loading 过程**阻塞 UI**，用户体验差

#### useTransition 的解决思路

`useTransition` 的核心行为是：**切换 UI 时先继续展示旧 UI，等新 UI 加载完成后再切换展示**——用户始终看到可用界面，不会被 loading 打断。

---

### 实现 useTransition 的概念映射

将 UI 层面的行为翻译为源码层面的更新机制：

| UI 概念 | 源码概念 |
|---------|---------|
| 切换 UI | **触发更新** |
| 先展示旧 UI，等新 UI 就绪后再展示 | 切换到新 UI 对应的更新是**低优先级更新** |

因此，`useTransition` 的本质是：在用户主动触发 UI 切换时，将这次 `setState` 标记为**低优先级并发更新**，让 React 在后台渲染新 UI 的同时继续展示旧 UI；待新 UI 渲染完成后，再 commit 切换。

---

### 并发策略与本次注释的关系

结合课程中的并发策略调整，完整逻辑如下：

```
默认行为（mount / 普通 setState）
  ↓
同步更新（SyncLane）
  ↓
首屏尽快渲染，用户立即看到内容

使用 useTransition 后的 setState
  ↓
低优先级并发更新（如 DefaultLane / TransitionLane）
  ↓
旧 UI 继续展示 → 后台渲染新 UI → 渲染完成后切换
```

本次在 `updateContainer` 中添加的注释，对应的是上述流程的**第一条路径**：确保 mount 更新走同步优先级，为后续 `useTransition` 提供「默认同步、按需并发」的策略基础。

---

### 核心价值

1. **明确并发策略边界** — 默认同步、并发特性按需启用，避免所有更新都走并发路径
2. **锁定 mount 优先级改造点** — 首屏更新是「默认同步」策略的入口，需在 `updateContainer` 中通过 Scheduler 上下文控制
3. **为 useTransition 铺路** — 只有先保证普通更新同步、并发更新可区分，`useTransition` 的低优先级更新才有意义
