## 最小必测（4条）

### TC01 多节点重排（核心）

- **操作**

  - 点击 `ul` 两次（触发 `setCount`，列表在 `[1,2,3]` 和 `[3,2,1]` 间切换）。
- **预期**
  - 列表顺序切换正确。
  - 发生"移动"而不是整棵重建。
- **覆盖点**
  - `reconcileChildrenArray`
  - `updateFromMap`
  - `lastPlacedIndex` 移动判定
  - `getHostSibling` + `insertChildToContainer`
  - `onClickCapture` 事件收集/触发

### TC02 单节点替换（类型变化）

- **操作**
  - 手动把初始 mode 改成 `h1`，确认渲染后再改成 `text`（刷新观察）。
  - 或使用 `main-update.tsx` 的 `setMode('h1') -> setMode('text')`。
- **预期**
  - `h1` 被移除，文本节点插入。
  - 触发删除 + 插入两类副作用。
- **覆盖点**
  - `reconcileSingleElement`（type 不同分支）
  - `deleteRemainingChildren`
  - `commitDeletion` + `commitPlacement`

### TC03 子树删除 + useState 更新

- **操作**
  - 进入 `mode='child'`，点击一次让 `count` 变化。
  - 再切到兜底分支（`section`）。
- **预期**
  - `child` 分支文本更新正确（`useState` update 正常）。
  - 切到 `section` 时旧子树完整卸载，无残留。
- **覆盖点**
  - `updateState` / `processUpdateQueue`
  - `commitNestedComponent`
  - `recordHostChildrenToDelete` + `removeChild`

### TC04 Fragment 两种形态

- **操作**
  - 运行 `fg1`（顶层 `<>...</>`）。
  - 再运行 `fg2`（`ul` 内嵌 fragment）。
- **预期**
  - Fragment 本身不生成额外 DOM 容器。
  - 子节点结构正确挂载、切换正常。
- **覆盖点**
  - `isUnkeyedTopLevelFragment`
  - `createFiberFromFragment` / `updateFragment`
  - `beginWork` 的 `Fragment` 分支

## 建议顺序

### ⚠️ 理论上未覆盖但实际影响小的边界

1. **多节点数组里混入 null/undefined/boolean**
   - `updateFromMap` 返回 `null` 的分支（L262）
   - 你的 demo 里没有这种写法，实际项目遇到再补

2. **多节点数组里嵌套数组**（L252 的 `Array.isArray(element)` 分支）
   - 虽然 TC04 有 fragment，但没测 `[<li/>, [<li/>, <li/>]]` 这种显式嵌套
   - 正常写法基本不会这么用，可以忽略

3. **单节点 key 相同但 type 变化时的兄弟节点删除**
   - TC02 只测了单子节点场景
   - 如果你想测 `<div key="x"/>` → `<span key="x"/>` + 兄弟节点，需要额外 case

4. **FunctionComponent 中途抛错的 workLoop catch 分支**
   - 你代码里有 try/catch，但 demo 里没有故意触发错误的组件

5. **事件 stopPropagation**
   - TC01 只测了捕获触发，但没测中途 `e.stopPropagation()` 打断冒泡

### 结论

**对于你当前的实现和 demo，这 4 条已经足够！**

理由：
1. **主路径 100% 覆盖**：mount、update、单节点、多节点、移动、删除、Fragment、Hooks、事件
2. **未覆盖的都是边界/异常分支**，在你的 demo 里根本不会走到
3. 如果后续发现 bug，再针对性补用例，而不是提前为"可能存在的问题"写一堆测试
