### Q1: ensureRootIsScheduled 为什么在 maxPendingLane === NoLane 时要取消任务？

<details>
<summary><strong>A:</strong>(点击展开/收起)</summary>

#### 3 句话版本

**Q：为什么 `NoLane` 时要取消任务？**

**A：因为能走到这里，任务肯定已经执行完了。**

---

#### 为什么肯定执行完了？

看代码执行顺序：

```typescript
performConcurrentWorkOnRoot(root)
  └─ renderRoot(...)  // 渲染
  └─ commitRoot(root)  // 提交
      └─ markRootFinished(root, lane)  // ← 这里把 lane 从 pendingLanes 删掉
      └─ ensureRootIsScheduled(root)
          └─ maxPendingLane = NoLane  // ← 因为上面删掉了
```

**逻辑链**：
1. 只有 `commitRoot` 才会调用 `markRootFinished`
2. `markRootFinished` 才会把 lane 从 `pendingLanes` 删掉
3. 删掉后 `pendingLanes` 才可能变成 `NoLanes`
4. 只有 commit 完成，任务才算结束

**所以**：能进入 `maxPendingLane === NoLane` 这个分支，说明任务已经 commit 完了，已经结束了。

---

#### 那为什么要取消？

因为要清理状态。

```typescript
// 任务完成前
root.pendingLanes = 0b0100
root.callbackNode = Task#1

// 任务完成后
root.pendingLanes = 0b0000  // ← 清空了
root.callbackNode = ???     // ← 也要清空，保持一致
```

**就这么简单**：没活干了（`pendingLanes` 空了），就把任务句柄也清空（`callbackNode = null`）。

---

#### 补充：什么是"任务句柄"？

**任务句柄 = Scheduler 返回的任务 ID**

就像你点外卖，商家给你一个取餐号，这个号就是"句柄"。

##### 具体来说

```typescript
// 你安排一个任务
const task = scheduleCallback(NormalPriority, () => {
  console.log('干活');
});

// task 就是"任务句柄"
// 它是 Scheduler 返回的一个对象，代表"这个任务"
```

**用途：**

```typescript
// 1. 你可以用它取消任务
unstable_cancelCallback(task);  // 告诉 Scheduler：别执行这个任务了

// 2. 你可以用它判断"是不是同一个任务"
if (root.callbackNode === task) {
  console.log('是同一个任务');
}
```

##### 在 React 里

```typescript
// 安排任务
root.callbackNode = scheduleCallback(priority, performConcurrentWorkOnRoot);
//                  ↑
//                  返回值是一个对象，存起来

// 取消任务
unstable_cancelCallback(root.callbackNode);
//                      ↑
//                      传给 Scheduler，让它取消这个任务
```

**就是个引用**，指向 Scheduler 里的那个任务。

**一句话**：`callbackNode` = 外卖取餐号，用来标识和取消任务。

</details>

### Q2: flushPassiveEffects 里如果有高优先级更新，为什么要检查 callbackNode 并 return null？调用栈是什么？

<details>
<summary><strong>A:</strong>(点击展开/收起)</summary>

> 对应代码：`workLoop.ts:169-183`

#### 核心原因

**因为发现"自己已经被替换了"，继续执行是浪费计算。**

`performConcurrentWorkOnRoot` 开头的这段代码：

```typescript
const curCallback = root.callbackNode;  // 记录当前任务句柄
const didFlushPassiveEffect = flushPassiveEffects(root.pendingPassiveEffects);
if (didFlushPassiveEffect) {
  if (root.callbackNode !== curCallback) {
    return null;  // 立即退出
  }
}
```

**检查逻辑**：如果 `useEffect` 回调执行后，`root.callbackNode` 变了，说明有更高优先级任务插入并取消了当前任务，应该立即退出。

---

#### 完整调用栈（全部是同步执行）

```typescript
performConcurrentWorkOnRoot(root)
  │
  ├─ curCallback = root.callbackNode  // Task#1 (DefaultLane)
  │
  ├─ flushPassiveEffects(root.pendingPassiveEffects)  // ← 同步执行
  │   │
  │   ├─ commitHookEffectListCreate(Passive | HookHasEffect, effect)
  │   │   │
  │   │   └─ effect.create()  // ← 同步执行 useEffect 回调
  │   │       │
  │   │       └─ unstable_runWithPriority(ImmediatePriority, () => {
  │   │           │
  │   │           └─ onKick()  // ← 同步调用
  │   │               │
  │   │               ├─ setCount(n => n + 1000)  // ← 同步
  │   │               │   │
  │   │               │   └─ dispatchSetState
  │   │               │       │
  │   │               │       └─ scheduleUpdateOnFiber(fiber, SyncLane)  // ← 同步
  │   │               │           │
  │   │               │           └─ ensureRootIsScheduled(root)  // ← 同步
  │   │               │               │
  │   │               │               ├─ maxPendingLane = SyncLane
  │   │               │               ├─ prevPriority = DefaultLane
  │   │               │               ├─ 不相等！取消旧任务
  │   │               │               ├─ unstable_cancelCallback(Task#1)
  │   │               │               │
  │   │               │               ├─ if (maxPendingLane === SyncLane) {
  │   │               │               │     scheduleSyncCallback(performSyncWorkOnRoot)
  │   │               │               │     scheduleMicroTask(flushSyncCallback)
  │   │               │               │     newCallbackNode = null  // SyncLane 不返回句柄
  │   │               │               │   }
  │   │               │               │
  │   │               │               ├─ root.callbackNode = null      // ← 关键变化！
  │   │               │               └─ root.callbackPriority = SyncLane
  │   │               │
  │   │               └─ setItems(30)  // 同样的流程
  │   │
  │   └─ flushSyncCallback()  // 将 performSyncWorkOnRoot 加入微任务队列
  │       └─ queueMicrotask(() => performSyncWorkOnRoot(root))
  │
  ├─ // flushPassiveEffects 返回 true
  │
  ├─ if (didFlushPassiveEffect) {  // ← true
  │     if (root.callbackNode !== curCallback) {  // ← null !== Task#1 ✅
  │       return null;  // ← 立即退出！
  │     }
  │   }
  │
  └─ （不会执行到这里）
```

---

#### 关键点 1：全部是同步执行

**重要**：从 `flushPassiveEffects` 开始，到 `ensureRootIsScheduled` 修改 `root.callbackNode`，**整个调用栈都是同步的**，没有任何异步环节。

```typescript
// 时间线（单线程同步执行）
T1: performConcurrentWorkOnRoot 开始
    └─ curCallback = Task#1

T2: flushPassiveEffects 开始（同步）
    └─ useEffect 回调执行（同步）
        └─ unstable_runWithPriority(ImmediatePriority, onKick)（同步）
            └─ setCount()（同步）
                └─ scheduleUpdateOnFiber（同步）
                    └─ ensureRootIsScheduled（同步）
                        └─ root.callbackNode = null  // ← 这里改了！

T3: flushPassiveEffects 返回 true（同步）

T4: 检查 root.callbackNode !== curCallback（同步）
    └─ null !== Task#1  ✅ 成立
    └─ return null  // ← 立即退出

T5: performConcurrentWorkOnRoot 结束

T6: （微任务队列）执行 performSyncWorkOnRoot
```

---

#### 关键点 2：为什么 root.callbackNode 变成 null？

不是因为"被清空了"，而是因为 **SyncLane 任务用微任务调度，不通过 Scheduler**：

```typescript
// ensureRootIsScheduled 函数内部
let newCallbackNode = null;

if (maxPendingLane === SyncLane) {
  // 同步优先级，用微任务调度
  scheduleSyncCallback(performSyncWorkOnRoot.bind(null, root));
  scheduleMicroTask(flushSyncCallback);
  // ⚠️ 注意：这里没有给 newCallbackNode 赋值
  // 所以 newCallbackNode 保持为 null
} else {
  // 其他优先级，用宏任务调度
  newCallbackNode = scheduleCallback(...);  // 这里才会返回 task 对象
}

root.callbackNode = newCallbackNode;  // ← 对于 SyncLane，赋值为 null
root.callbackPriority = curPriority;  // ← SyncLane
```

**原因**：
- 同步任务用 `queueMicrotask` 调度，不走 Scheduler
- 不返回 `callbackNode`（任务句柄）
- 所以 `newCallbackNode` 保持为 `null`
- 从并发任务（有 `callbackNode`）变成了同步任务（没有 `callbackNode`）

---

#### 关键点 3：为什么要 return null？

**因为发现"自己已经被取消了"！**

```typescript
// 执行前的状态
root.callbackNode = Task#1 (performConcurrentWorkOnRoot, DefaultLane)
root.callbackPriority = DefaultLane

// flushPassiveEffects 执行后的状态
root.callbackNode = null  // ← 被改变了
root.callbackPriority = SyncLane
// 同时微任务队列里有了：performSyncWorkOnRoot (SyncLane)

// 所以当前这个 Task#1 不应该继续执行了
// 应该让微任务队列里的 performSyncWorkOnRoot 去执行
```

---

#### 如果不 return null 会怎样？

```typescript
// ❌ 如果继续执行
performConcurrentWorkOnRoot(root)
  ├─ flushPassiveEffects() 
  │   └─ 触发了 SyncLane 更新
  │       └─ 微任务队列已安排：performSyncWorkOnRoot
  │
  ├─ 不检查，继续往下走
  │
  ├─ renderRoot(root, DefaultLane)  // ← 浪费计算！
  │   └─ 渲染低优先级 DefaultLane
  │   └─ 耗时 400ms
  │
  └─ commitRoot(root)  // ← 提交了低优先级的结果

// 问题：
// 1. 高优先级 SyncLane 被延迟了 400ms（用户体验差）
// 2. DefaultLane 的 400ms 计算浪费了（后面还要重新渲染）
```

---

#### 有了 return null 的正确流程

```typescript
// ✅ 正确流程
performConcurrentWorkOnRoot(root)  // Task#1
  ├─ curCallback = Task#1
  │
  ├─ flushPassiveEffects()
  │   └─ 触发 SyncLane 更新
  │       ├─ unstable_cancelCallback(Task#1)  // 取消自己
  │       ├─ root.callbackNode = null
  │       └─ 微任务队列：performSyncWorkOnRoot
  │
  ├─ if (root.callbackNode !== curCallback) {  // null !== Task#1
  │     return null;  // ← 立即退出，不做低优先级渲染
  │   }
  │
  └─ （退出）

// Scheduler 收到 null，Task#1 结束

// 微任务队列立即执行
performSyncWorkOnRoot(root)
  └─ renderRoot(root, SyncLane, false)  // 立即渲染高优先级
  └─ commitRoot(root)  // 用户立即看到更新

// 结果：
// ✅ 高优先级立即执行（用户体验好）
// ✅ 避免了低优先级的浪费计算
```

---

#### 完整的状态变化

```typescript
// 初始状态（第一次渲染完成后）
root.pendingLanes = DefaultLane
root.callbackNode = Task#1 (performConcurrentWorkOnRoot, DefaultLane)
root.callbackPriority = DefaultLane
root.pendingPassiveEffects.update = [useEffect 的 effect]

// ↓ Scheduler 调度 Task#1
performConcurrentWorkOnRoot(root) 开始
  curCallback = Task#1  // 快照

// ↓ 执行 flushPassiveEffects
  useEffect 回调执行（同步）
    unstable_runWithPriority(ImmediatePriority, () => {
      setCount(n => n + 1000)
        → scheduleUpdateOnFiber(fiber, SyncLane)
          → root.pendingLanes = SyncLane | DefaultLane
          → ensureRootIsScheduled(root)
            → maxPendingLane = SyncLane
            → prevPriority = DefaultLane
            → 不相等！有更高优先级
            → unstable_cancelCallback(Task#1)
            → scheduleSyncCallback(performSyncWorkOnRoot)
            → root.callbackNode = null  // ← 改变了！
            → root.callbackPriority = SyncLane
    })

// ↓ flushPassiveEffects 返回 true

// ↓ 检查
  root.callbackNode !== curCallback
  null !== Task#1  ✅

// ↓ 退出
  return null

// ↓ 微任务队列执行
  performSyncWorkOnRoot(root)
    → 立即渲染高优先级更新
```

---

#### 总结

##### 核心要点

1. **调用栈是同步的**：`flushPassiveEffects` 及其内部的所有调用（包括 `useEffect` 回调、`setState`、`scheduleUpdateOnFiber`、`ensureRootIsScheduled`）都是**同步执行**的

2. **为什么检查 `callbackNode`**：因为 `flushPassiveEffects` 里可能触发高优先级更新，而高优先级更新会修改 `root.callbackNode`（取消当前任务，对于 SyncLane 会设为 `null`）

3. **为什么 `return null`**：因为发现自己（当前 Task#1）已经被取消了，不应该继续执行低优先级渲染，应该让微任务队列里的高优先级任务去执行

4. **为什么 `callbackNode` 是 `null`**：因为 SyncLane 任务用微任务调度，不通过 Scheduler，没有返回任务句柄，所以 `newCallbackNode` 为 `null`

##### 收益

- **避免浪费计算**：低优先级渲染会被高优先级覆盖，提前退出避免无用功
- **提升用户体验**：高优先级更新立即执行，响应更快
- **保证调度正确性**：基于最新状态做决策

##### 一句话总结

**这段代码通过同步执行 `useEffect` 回调并检查 `callbackNode` 变化，可以及时发现高优先级更新插入的情况，立即退出当前低优先级任务，避免浪费计算并提升用户体验。整个检测过程都是同步的，不涉及任何异步操作。**

</details>

### Q3: 为什么 performConcurrentWorkOnRoot 在 renderRoot 后要调用 ensureRootIsScheduled(root)？

<details>
<summary><strong>A:</strong>(点击展开/收起)</summary>

> 对应代码：`workLoop.ts:202`

#### 核心结论

**在当前简化实现里**：这行代码更像是"对齐官方 React 结构"的收尾检查，实际作用较弱。

**在完整 React 里**：这是 render attempt 结束后的必要复核步骤，用于重新评估 root 的调度状态。

---

#### 我的困惑过程

一开始我认为这行代码是为了"提前安排低优先级任务"或"处理时间切片中断"，但经过深入分析发现：

1. **不是为了处理高优先级插入**
   - 如果 render 过程中有新的更新，`setState` 会触发 `scheduleUpdateOnFiber -> ensureRootIsScheduled`
   - 不需要等到 L202 这里

2. **不是时间切片恢复的核心**
   - 时间切片恢复靠的是：
     ```typescript
     if (exitStatus === RootIncomplete) {
       return performConcurrentWorkOnRoot.bind(null, root);  // 返回 continuation
     }
     ```
   - 以及 `renderRoot` 里的 `wipRootRenderLane === lane` 判断（从断点继续）

3. **不是专门处理 skipped lanes**
   - 低优先级 lane 被跳过后，会在 `commitRoot -> markRootFinished -> ensureRootIsScheduled` 处理
   - 不需要 L202

---

#### 那它到底有什么用？

通过对比 `my-react-main-2xiao` 参考实现和 React 18 官方源码，确认了这是 React 官方 work loop 的标准结构：

**每次 render attempt 结束后，统一重新确认 root 的调度状态。**

它和后面的判断是一组配合使用：

```typescript
// L202: 重新评估调度状态
ensureRootIsScheduled(root);

// L206-212: 检查调度状态是否发生变化
if (exitStatus === RootIncomplete) {
  if (root.callbackNode !== curCallbackNode) {
    // callbackNode 变了，说明有更高优先级任务插入
    // 当前任务应该被取消，不返回 continuation
    return null;
  }
  // callbackNode 没变，可以续跑
  return performConcurrentWorkOnRoot.bind(null, root);
}
```

**作用**：在 render 后、决定是否返回 continuation 前，重新确认一次调度状态，确保返回的 continuation 是正确的。

---

#### 对比：为什么 performSyncWorkOnRoot 没有这一行？

```typescript
// performSyncWorkOnRoot（同步渲染）
renderRoot(root, SyncLane, false)  // 不可中断
// ❌ 没有 ensureRootIsScheduled
commitRoot(root)

// performConcurrentWorkOnRoot（并发渲染）
renderRoot(root, lane, true)  // 可中断
// ✅ 有 ensureRootIsScheduled
if (exitStatus === RootIncomplete) {
  // 可能需要返回 continuation
}
commitRoot(root)
```

**关键区别**：并发渲染**可能被中断并返回 continuation**，需要在返回前确认调度状态是否还适合续跑。

同步渲染一口气执行完，不存在"续跑"问题，所以不需要这个检查。

---

#### 在当前简化实现里的情况

当前项目中，`root.pendingLanes` 的修改几乎都会触发 `ensureRootIsScheduled`：

1. **新的更新插入**
   ```typescript
   setState
     -> scheduleUpdateOnFiber
     -> markRootUpdated
     -> ensureRootIsScheduled  // ← 已经调用了
   ```

2. **Skipped lanes**
   - 低优先级 update 被跳过时进入 `baseQueue`
   - 但之前创建时已经 `root.pendingLanes |= lane`
   - 最终在 `commitRoot -> markRootFinished -> ensureRootIsScheduled` 处理

3. **Interleaved updates**
   - 当前没有真实 React 的 `interleavedUpdatedLanes` 机制
   - 本质还是走 `setState -> scheduleUpdateOnFiber -> ensureRootIsScheduled`

**所以在当前简化实现里，L202 这行的实际作用很弱，更多是防御性编程。**

---

#### 完整 React 里为什么需要？

真实 React 的 render 过程中，有很多机制会改变 root 的调度状态，**这些变化不都是通过 setState 触发的**：

##### 1. Suspense 挂起
```typescript
// 组件渲染时发现数据未就绪
throw promise

// React 会：
// - 标记 lane 为 suspended
// - 修改 root 的后续调度状态
// - 等待 promise 完成
```

##### 2. Ping（恢复）
```typescript
// 之前挂起的 promise 完成了
promise.then(() => {
  // React 会：
  // - 标记之前挂起的 lane 可以重试
  // - 修改 root 的调度状态
})
```

##### 3. Interleaved updates
```typescript
// 并发 render 过程中，浏览器让出主线程
// 期间又来了新的更新
// React 要记录：render 过程中夹进来了新的 update
```

##### 4. Skipped lanes
```typescript
// 本轮 render 只处理高优先级 lane
// 低优先级 lane 被跳过
// React 要记住：这些低优先级后面还要继续处理
```

##### 5. 其他复杂机制
- Retry lane
- Entangled lanes
- Deferred lane
- Prerender / hydration 相关状态

**所以官方在一次 render attempt 后统一调用：**

```typescript
ensureRootIsScheduled(root)
```

**语义是**：

> "刚才 render 过程中，root 的状态可能通过各种方式发生了变化，现在重新评估一次：接下来到底该不该安排新任务、安排什么优先级的任务。"

然后再根据 `root.callbackNode` 是否变化，决定是返回 continuation 还是 `return null`。

---

#### 总结

##### 当前简化实现
- **定位**：防御性代码 / 对齐官方结构
- **可以删吗**：大概率可以，不影响主流程
- **为什么保留**：为了和官方 React 结构一致，方便后续扩展

##### 完整 React
- **定位**：render attempt 结束后的必要收尾步骤
- **可以删吗**：不能，是核心调度逻辑的一部分
- **作用**：统一重新计算 root 下一步该调度什么，并决定当前 callback 是否还能返回 continuation

##### 什么时候能真正理解它的必要性？

**等实现 Suspense / ping / retry / entanglement 等复杂功能时，这一行的必要性会更加明显。**

到那时，render 过程中会有更多"不通过 setState 就能改变 root 调度状态"的路径，这个统一的复核点就变得不可或缺了。

---

#### 一句话总结

**这行代码是 React 官方 work loop 的标准结构：每次 render attempt 结束后，重新评估 root 的调度状态，确保后续的 continuation 决策是基于最新状态做出的。在当前简化实现里作用较弱，但在完整 React 里是必要的调度收尾步骤。**

</details>

### Q4: 时间切片中断后的续跑机制是什么？如何判断是续跑还是放弃？

<details>
<parameter name="<strong>A:</strong>(点击展开/收起)</summary>

> 对应代码：`workLoop.ts:204-214`

#### 核心机制

这段代码实现了**时间切片中断后的续跑逻辑**：

```typescript
if (exitStatus === RootIncomplete) {
  // 执行中断
  if (root.callbackNode !== curCallbackNode) {
    // 代表有更高优先级的任务插进来
    return null;  // 放弃续跑
  }
  return performConcurrentWorkOnRoot.bind(null, root);  // 返回 continuation，稍后续跑
}
```

**决策逻辑**：
1. **检查渲染是否中断**：`exitStatus === RootIncomplete` 表示因时间切片而中断（还没完成）
2. **检查是否被高优先级打断**：`root.callbackNode !== curCallbackNode` 检查渲染期间是否有更高优先级任务插入
3. **决定续跑还是放弃**：
   - 被打断：`return null`（放弃当前任务）
   - 没被打断：`return performConcurrentWorkOnRoot.bind(null, root)`（返回 continuation）

#### 场景 1：正常时间切片中断（没有高优先级插入）

- `performConcurrentWorkOnRoot` 返回 continuation 让 Scheduler 稍后继续

#### 关键问题：`unstable_shouldYield()` 返回 `true` 的原因

**唯一原因：时间片到期了（默认 5ms）**

```typescript
// Scheduler 的 unstable_shouldYield 实现（简化版）
function unstable_shouldYield() {
  const currentTime = getCurrentTime();
  const deadline = startTime + QUANTUM_SIZE;  // QUANTUM_SIZE = 5ms
  
  return currentTime >= deadline;  // 只检查时间是否到了
}
```

**它只检查**：
- 当前时间是否超过了时间片的截止时间

**它不检查**：
- ❌ 是否有高优先级任务
- ❌ 用户是否点击
- ❌ `root.callbackNode` 是否变化
- ❌ 是否调用了 `setState`

**场景 2 中的两个独立事件**：

```typescript
// 时间线

  → 修改 root.callbackNode = null
  → 标记"需要放弃续跑"

事件 2: T0+5ms - 时间片到期
  → unstable_shouldYield() 返回 true
  → 跳出渲染循环
  → 返回 RootIncomplete

// 然后检查
if (root.callbackNode !== curCallbackNode) {
  // ← 检测到事件 1 的影响
  return null;
}
```

#### 可以删除这段代码吗？

**不能删除！这是时间切片和并发渲染的核心逻辑。**

##### 如果删除会怎样？

```typescript
// ❌ 删除后

  // 直接返回 continuation，不检查
  return performConcurrentWorkOnRoot.bind(null, root);

// 问题：
// 1. 即使有高优先级任务插入，也会继续续跑低优先级任务
// 2. 高优先级任务被延迟执行
// 3. 用户体验差
```

##### 为什么必须检查？

```typescript
// ✅ 有检查
if (root.callbackNode !== curCallbackNode) {
  // 发现自己被取消了，不续跑
  return null;
}
return performConcurrentWorkOnRoot.bind(null, root);

// 作用：
// 1. 确保高优先级任务能立即执行
// 2. 避免浪费计算（低优先级的续跑会被高优先级覆盖）
// 3. 正确的调度语义
```

#### 与前面检查点的对比

代码中有两个 `callbackNode` 检查点，它们互相配合：

```typescript
// 检查点 1: L171-183 (flushPassiveEffects 后)
const curCallback = root.callbackNode;
const didFlushPassiveEffect = flushPassiveEffects(...);
if (didFlushPassiveEffect) {
  if (root.callbackNode !== curCallback) {
    return null;  // useEffect 里有高优先级更新
  }
}

// 检查点 2: L204-214 (renderRoot 后)
const curCallbackNode = root.callbackNode;
const exitStatus = renderRoot(...);
if (exitStatus === RootIncomplete) {
  if (root.callbackNode !== curCallbackNode) {
    return null;  // render 过程中有高优先级更新
  }
  return performConcurrentWorkOnRoot.bind(null, root);  // 续跑
}
```

**区别**：
- **检查点 1**：在 render **之前**检查，防止开始就没必要的渲染
- **检查点 2**：在 render **中断后**检查，决定是否续跑

#### 总结

##### 核心作用

这段代码实现了**时间切片中断后的续跑机制**，同时确保高优先级任务能正确打断低优先级任务。

##### 不能删除的原因

1. **时间切片核心逻辑**：`return performConcurrentWorkOnRoot.bind(null, root)` 是时间切片续跑的唯一方式
2. **调度正确性**：检查 `callbackNode` 确保不会续跑已被取消的任务
3. **用户体验**：保证高优先级任务能立即执行

##### 触发条件

- **RootIncomplete**：渲染因时间切片中断（`unstable_shouldYield()` 返回 true）
- **callbackNode 变化**：渲染期间有高优先级更新插入并取消了当前任务
- **callbackNode 不变**：正常时间切片，没有打断，可以续跑

##### 时间切片的工作机制

```typescript
// 两个独立机制配合工作
机制 1: unstable_shouldYield()
  → 决定**何时**中断（基于时间，5ms）
  → 不关心优先级、用户交互等

机制 2: callbackNode 检查
  → 决定中断后**是否续跑**（基于优先级）
  → 检测是否有更高优先级任务插入
```

##### 一句话总结

**这段代码是 React 并发渲染和时间切片的核心机制：当渲染因时间切片中断时，检查是否有更高优先级任务插入，决定是放弃当前任务（return null）还是返回 continuation 让 Scheduler 稍后继续执行。不能删除，是并发模式的必要逻辑。**

##### 场景 A：高优先级更新只影响部分组件（真实 React 常见情况）

#### 为什么要这样设计？

##### 1. 保证渲染一致性

```typescript
// 如果续跑任务 1
renderRoot(root, DefaultLane)
  └─ 从 fiber30 继续渲染
      └─ 但 fiber0-fiber29 是基于旧的 state 渲染的
      └─ fiber30-fiber99 是基于新的 state 渲染的
      └─ 不一致！可能出现 bug
```

##### 2. 简化实现

重新渲染比"合并"旧的工作更简单，也更可靠。

##### 3. 高优先级更新通常很快

在实际应用中，高优先级更新（如用户交互）通常只影响少数组件。

---

#### React 如何减少重复渲染？

##### 1. Bailout 优化

```typescript
// React 的 bailout 机制
if (
  oldProps === newProps &&
  oldState === newState &&
  oldContext === newContext
) {
  // 跳过子树，直接复用
  return bailoutOnAlreadyFinishedWork(fiber);
}
```

##### 2. Lanes 优先级合并

```typescript
// 如果两个更新非常接近，React 可能会合并
ensureRootIsScheduled(root)
  → 发现 SyncLane 和 DefaultLane 都需要处理
  → 可能选择一起处理（避免重复渲染）
```

##### 3. 使用 useMemo / React.memo

```typescript
const MemoizedBigList = React.memo(BigList);
// 即使重新渲染，如果 props 没变，BigList 内部不会重新执行
```

---

#### 总结

##### 被打断任务的状态

1. **pendingLanes 保留**：`DefaultLane` 不会被清除，等待重新调度
2. **进度丢失**：`workInProgress` 和 `wipRootRenderLane` 被覆盖，之前的渲染工作丢失
3. **重新调度**：高优先级任务完成后，`ensureRootIsScheduled` 会重新调度 `DefaultLane`
4. **从头开始**：重新调度的任务因为 `isResume = false`，会从头开始渲染

##### 是否会重复渲染？

**在当前简化实现中：是的，会重复渲染 2 次所有组件**

**在真实 React 中：不会，因为有 bailout 优化**
- 任务 2 只渲染变化的部分（如 Header）
- 任务 3 只渲染另一部分的变化（如 BigList）
- 总体上不会重复渲染所有组件

##### 这是并发模式的代价吗？

**是的，这是并发模式为了响应性而付出的代价：**
- 优势：高优先级更新立即响应（用户体验好）
- 代价：可能浪费低优先级的计算（性能）

但真实 React 通过 bailout、lane 合并等优化，把这个代价降到了很低。

##### 一句话总结

**高优先级任务完成后，被打断的低优先级任务会被重新调度为新任务，从头开始渲染（因为 `wipRootRenderLane` 被覆盖导致 `isResume = false`）。在当前简化实现中会导致重复渲染，但真实 React 通过 bailout 优化，只渲染真正变化的部分，避免了大量重复计算。**

<summary><strong>Q6: <code>unstable_shouldYield</code> 和 <code>didTimeout</code> 分别是什么？有什么区别和作用？</strong></summary>

## 问题

在并发渲染中，看到两个关键概念：

```typescript
// workLoopConcurrent 中
while (workInProgress !== null && !unstable_shouldYield()) {
  performUnitOfWork(workInProgress);
}

// performConcurrentWorkOnRoot 中
function performConcurrentWorkOnRoot(root: FiberRootNode, didTimeout?: boolean) {
  const needSync = updateLane === SyncLane || didTimeout;
  const exitStatus = renderRoot(root, updateLane, !needSync);
}
```

这两个分别是什么含义？有什么区别？是谁调用的？

---

## 回答

这两个是**时间切片和任务调度的核心概念**，职责完全不同：
- **`unstable_shouldYield`**：微观层面，负责**主动中断渲染**
- **`didTimeout`**：宏观层面，负责**防止任务饥饿**

---

### 1️⃣ `unstable_shouldYield` - 时间片守护者

#### 是什么？

```typescript
// 从 Scheduler 包导入的函数
import { unstable_shouldYield } from 'scheduler';

// Scheduler 内部实现（简化版）
function shouldYieldToHost() {
  const timeElapsed = getCurrentTime() - startTime;
  
  if (timeElapsed < frameInterval) {  // frameInterval = 5ms
    return false;  // 时间片还没用完
  }
  
  return true;  // 时间片用完了，该让出主线程了
}
```

#### 作用

**检查当前时间片（默认 5ms）是否用完，决定是否应该让出主线程。**

#### 在哪里使用？

在**并发渲染的工作循环**中，每次渲染 Fiber 节点前都检查：

```typescript
function workLoopConcurrent() {
  while (workInProgress !== null && !unstable_shouldYield()) {
    //                              ↑
    //                    每次循环都检查时间片
    performUnitOfWork(workInProgress);
  }
}
```

**检查逻辑**：
- `workInProgress !== null`：还有节点要渲染
- `!unstable_shouldYield()`：时间片还没用完

**一旦返回 `true`**：
- 立即跳出循环
- 返回 `RootIncomplete`（渲染未完成）
- Scheduler 让出主线程，浏览器处理用户输入、动画等
- 稍后再继续渲染

#### 调用者

**React reconciler**，在每个 Fiber 节点的渲染前调用（每次 `performUnitOfWork` 前检查）。

---

### 2️⃣ `didTimeout` - 任务过期标志

#### 是什么？

```typescript
function performConcurrentWorkOnRoot(
  root: FiberRootNode,
  didTimeout?: boolean  // ← Scheduler 调用时传入的参数
): any {
```

**一个布尔参数**，由 **Scheduler 在调用回调时传入**。

#### 作用

**告诉 React："这个任务已经过期了（等待太久了），必须立即执行完，不能再切片中断。"**

#### Scheduler 如何计算并传入？

看 Scheduler 的实现：

```javascript
// Scheduler 的 workLoop 函数
function workLoop(hasTimeRemaining, initialTime) {
  var currentTime = initialTime;
  currentTask = peek(taskQueue);
  
  while (currentTask !== null) {
    if (currentTask.expirationTime > currentTime && shouldYieldToHost()) {
      // 任务没过期 且 时间片用完 → 中断
      break;
    }
    
    var callback = currentTask.callback;
    
    // ⚠️ 关键：计算任务是否过期
    var didUserCallbackTimeout = currentTask.expirationTime <= currentTime;
    
    // 调用回调时传入 didTimeout
    var continuationCallback = callback(didUserCallbackTimeout);
    //                                   ↑
    //                           这就是 didTimeout 的来源
  }
}
```

**计算逻辑**：
```javascript
didTimeout = (currentTask.expirationTime <= currentTime)
```

- **`true`**：任务的过期时间 ≤ 当前时间（任务等太久了，过期了）
- **`false`**：任务还没过期

#### 在哪里使用？

```typescript
function performConcurrentWorkOnRoot(root: FiberRootNode, didTimeout?: boolean) {
  const updateLane = getHighestPriorityLane(root.pendingLanes);
  
  // ⚠️ 关键判断：是否需要同步模式
  const needSync = updateLane === SyncLane || didTimeout;
  //                                          ↑
  //                              如果过期了，强制同步模式
  
  // 决定是否使用时间切片
  const exitStatus = renderRoot(root, updateLane, !needSync);
  //                                              ↑
  //                 needSync=true → shouldTimeSlice=false（不可中断）
  //                 needSync=false → shouldTimeSlice=true（可时间切片）
}
```

**逻辑**：
- `didTimeout === true`：任务过期 → `needSync = true` → `shouldTimeSlice = false` → **同步模式（不可中断）**
- `updateLane === SyncLane`：本来就是同步优先级 → **同步模式**
- 其他情况：`needSync = false` → `shouldTimeSlice = true` → **并发模式（可时间切片）**

#### 调用者

**Scheduler**，在调度并发任务时计算并传入。

---

### 3️⃣ 两者的区别和关系

| 对比项 | `unstable_shouldYield` | `didTimeout` |
|--------|----------------------|--------------|
| **类型** | 函数 | 参数（布尔值） |
| **职责** | 检查时间片是否用完 | 标记任务是否过期 |
| **调用频率** | 每次渲染 Fiber 节点前调用 | 每次调度任务时计算一次 |
| **检查时机** | 渲染过程中（微观） | 调度层面（宏观） |
| **作用范围** | 决定是否**暂停当前渲染** | 决定是否**降级为同步模式** |
| **来源** | Scheduler 包导出的函数 | Scheduler 调用回调时传入 |
| **检查内容** | `(当前时间 - 开始时间) ≥ 5ms?` | `任务过期时间 ≤ 当前时间?` |
| **返回 true 的含义** | 时间片用完，暂停渲染 | 任务过期，必须立即完成 |

---

### 4️⃣ 完整执行流程示例

#### 场景 1：正常的并发渲染（时间切片）

```typescript
// T0: 调度开始
scheduleCallback(NormalPriority, performConcurrentWorkOnRoot.bind(null, root));
// Scheduler 设置：expirationTime = T0 + 5000ms

// T0+100ms: Scheduler 开始执行
// 计算：didTimeout = (5000 <= 100) → false（没过期）
performConcurrentWorkOnRoot(root, false);
  ↓
const needSync = SyncLane || false;  // false
  ↓
renderRoot(root, DefaultLane, true);  // shouldTimeSlice = true（可时间切片）
  ↓
workLoopConcurrent() {
  // T0+100ms
  while (workInProgress !== null && !unstable_shouldYield()) {
    performUnitOfWork(workInProgress);  // 渲染第 1 个组件
    // T0+101ms: unstable_shouldYield() → false（才用了 1ms）
    
    performUnitOfWork(workInProgress);  // 渲染第 2 个组件
    // T0+103ms: unstable_shouldYield() → false（才用了 3ms）
    
    performUnitOfWork(workInProgress);  // 渲染第 3 个组件
    // T0+105ms: unstable_shouldYield() → true（5ms 到了！）
    
    // 跳出循环
  }
}
  ↓
return RootIncomplete;  // 告诉 Scheduler：还没完成
  ↓
// Scheduler 让出主线程
// 浏览器处理用户输入、动画...
```

#### 场景 2：任务过期，防止饥饿

```typescript
// T0: 低优先级任务调度
scheduleCallback(IdlePriority, performConcurrentWorkOnRoot);
// Scheduler 设置：expirationTime = T0 + 5000ms

// T0+100ms ~ T0+4900ms: 不断有高优先级任务插队
// 低优先级任务一直在队列里排队，没机会执行

// T0+5100ms: Scheduler 终于轮到这个任务
// 计算：didTimeout = (5000 <= 5100) → true ⚠️ 过期了！
performConcurrentWorkOnRoot(root, true);
  ↓
const needSync = SyncLane || true;  // true
  ↓
renderRoot(root, IdleLane, false);  // shouldTimeSlice = false（降级为同步）
  ↓
workLoopSync() {
  // 不检查 unstable_shouldYield，一口气渲染完！
  while (workInProgress !== null) {
    performUnitOfWork(workInProgress);
    performUnitOfWork(workInProgress);
    performUnitOfWork(workInProgress);
    // ... 不管时间片，直到 workInProgress === null
  }
}
  ↓
return RootComplete;  // 必定完成
  ↓
commitRoot(root);  // 提交
```

### 5️⃣ 类比理解

#### `unstable_shouldYield`：交通信号灯

```
每个路口（Fiber 节点）都检查：
  - "现在是红灯吗？（时间片用完了吗？）"
  - 红灯 → 停车，让行人（浏览器）过马路
  - 绿灯 → 继续行驶（继续渲染）

特点：
  - 频繁检查（每个路口都看）
  - 局部决策（只管当前要不要停）
  - 可恢复（红灯变绿灯后继续）
```

#### `didTimeout`：快递加急标签

```
快递放在仓库太久了：
  - "这个快递必须今天送达！"
  - 不管堵不堵车（时间片），直接开到目的地
  - 中途不能停（不检查 shouldYield）

特点：
  - 一次性决策（调度时判断）
  - 全局影响（整个任务变同步）
  - 防止饥饿（优先级低的任务也能执行）
```

---

### 6️⃣ 总结

#### `unstable_shouldYield`（微观层面）

- **是谁**：Scheduler 提供的时间检查函数
- **检查什么**：当前时间片（5ms）是否用完
- **谁调用**：React 在并发渲染循环中调用（每次渲染一个 Fiber 节点前）
- **返回 true**：立即暂停渲染，让出主线程，保证浏览器响应性
- **目的**：实现时间切片，避免长时间阻塞主线程

#### `didTimeout`（宏观层面）

- **是谁**：Scheduler 传给回调的过期标志
- **检查什么**：任务是否等待太久（超过过期时间）
- **谁传入**：Scheduler 在调度任务时计算并传入
- **为 true**：任务必须立即完成，降级为同步模式（不可中断）
- **目的**：防止低优先级任务"饥饿"（永远得不到执行）

#### 两者配合的意义

```
unstable_shouldYield: 保证响应性
  → 每 5ms 让出主线程，用户交互流畅

didTimeout: 防止饥饿
  → 等太久的任务必须执行完，保证公平性

两者配合 = 既保证响应性，又防止饥饿
```

#### 一句话总结

**`unstable_shouldYield` 是"红绿灯"，每隔 5ms 检查一次是否该让路；`didTimeout` 是"加急标签"，告诉 React 这个任务等太久了必须立即跑完。两者配合实现了既流畅又公平的并发渲染。**

</details>
