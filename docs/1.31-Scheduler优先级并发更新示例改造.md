## 第三部分:主要知识点

### 本次 `main.ts` 改动的核心内容

#### 核心目标

**将一个简单的同步更新示例升级为基于 Scheduler 的并发更新示例**，模拟 React 真实的调度流程。

---

### 为什么要改动

结合课程截图中的理论，改动的动机包括：

#### 1. 原有的同步模型存在阻塞问题

- 之前的 `performWork` 是一个 `while` 同步死循环，会一次性执行完所有 `work.count`
- 如果 `count` 很大或单次工作量很重，会长时间占用主线程，导致页面卡顿、无法响应用户交互

#### 2. 验证并发更新的核心机制

- 课程提到并发更新的基础是"时间切片"（Time Slicing）
- 需要实践"如何中断任务""如何恢复任务""如何按优先级调度"

#### 3. 对齐 React 真实链路

- 课程流程图展示了 `交互 -> schedule -> perform -> 循环调度` 的闭环
- 需要在示例中模拟 `ensureRootIsScheduled` 的调度逻辑和优先级策略

---

### 实现了什么功能

#### 1. 多优先级任务调度

- 动态创建 4 个按钮，分别对应 4 种优先级（`ImmediatePriority`、`UserBlockingPriority`、`NormalPriority`、`LowPriority`）
- 点击按钮后，将对应优先级的任务加入 `workList` 队列

#### 2. 优先级排序与抢占

```typescript
function schedule() {
  const cbNode = getFirstCallbackNode();
  const curWork = workList.sort((w1, w2) => w1.priority - w2.priority)[0];

  // 策略逻辑
  if (!curWork) {
    curCallback = null;
    cbNode && cancelCallback(cbNode);
    return;
  }

  const { priority: curPriority } = curWork || {};

  if (curPriority === prevPriority) {
    return;
  }

  // 更高优先级的work
  cbNode && cancelCallback(cbNode);

  curCallback = scheduleCallback(curPriority, performWork.bind(null, curWork));
}
```

**关键逻辑:**
- 每次调度时，按优先级排序取出**最高优先级**的任务
- 如果出现更高优先级任务，会**取消当前正在执行的回调**（高优先级抢占）
- 相同优先级不重复调度，避免不必要的开销

#### 3. 时间切片与可中断执行

```typescript
function performWork(work: Work, didTimeout?: boolean) {
  /*
   * 1. work.priority
   * 2．饥饿问题
   * 3．时间切片
   */
  const needSync = work.priority === ImmediatePriority || didTimeout;

  while ((needSync || !shouldYield()) && work.count) {
    work.count--;
    insertSpan(work.priority + '');
  }

  // 中断执行 || 执行完
  prevPriority = work.priority;

  if (!work.count) {
    const workIndex = workList.indexOf(work);
    workList.splice(workIndex, 1);
    prevPriority = IdlePriority;
  }

  // 继续调度
  const prevCallback = curCallback;
  schedule();
  const newCallback = curCallback;

  if (newCallback && prevCallback === newCallback) {
    return performWork.bind(null, work);
  }
}
```

**三大核心机制:**

1. **时间切片判断:** 引入 `shouldYield()` 判断时间片是否用完，若用完则立即中断循环
2. **同步执行例外:** 两种情况会强制同步执行完：
   - `ImmediatePriority`（最高优先级，必须立即完成）
   - `didTimeout`（任务已过期，防止饥饿）
3. **任务续跑机制:** 如果任务被中断（`work.count > 0`），返回绑定函数供 Scheduler 在下一时间片继续执行

#### 4. 可视化优先级执行

- 每个优先级对应不同颜色（绿/紫/棕/红）
- 插入 `doSomeBuzyWork(1000000)` 放大每次渲染的耗时，方便观察中断与抢占效果
- 通过颜色变化可以直观看到优先级切换

---

### 完整闭环总结

按照课程截图中的流程图，本次改动实现了完整的调度闭环：

```
交互触发 
  ↓
schedule (调度阶段：按优先级排序、取消低优先级任务)
  ↓
performWork (执行阶段：时间切片、可中断、可续跑)
  ↓
schedule (完成后再次调度，形成循环)
```

**模拟了 React 并发更新的三大核心能力:**

1. **优先级调度** - 高优先级任务优先执行，低优先级任务可以被打断
2. **时间切片** - 长任务可以被拆分到多个时间片执行，避免阻塞主线程
3. **可中断恢复** - 低优先级任务被打断后，高优先级完成后可以继续执行

## 第四部分:个人 Q&A

### Q1: `Work.count` 是什么意思？是不是在模拟一个 work 里要处理多少个 Fiber？

是。这个示例里的 `count` 本质上是“剩余工作量计数器”，用来模拟一个任务还要执行多少个工作单元。可以把每次 `count--` 理解为“处理了一个 Fiber 单元”。

在真实 React 并发渲染中，循环通常是“处理一个 Fiber -> 判断是否让出线程 -> 再处理下一个 Fiber”；在这个 demo 里则用 `count` 做了等价抽象：

1. `count` 越大，任务越重，越容易出现中断与续跑
2. `count` 递减到 `0` 表示该 `work` 执行完成
3. 若时间片耗尽但 `count` 还大于 `0`，则任务会在后续调度中继续执行

所以你说“模拟一个 work 里需要处理 `count` 个 Fiber”这个理解是正确的。

### Q2: `cbNode`、`cancelCallback`、`curCallback` 分别是什么？`curCallback` 是类似 `timerId` 的数字吗？

不是数字。`curCallback` 以及 `cbNode` 的类型都是 `CallbackNode | null`，本质是 Scheduler 的“任务节点对象引用”。

先看类型定义：

```typescript
export interface CallbackNode {
  callback: FrameCallbackType;
  priorityLevel: number;
  expirationTime: number;
  next: CallbackNode | null;
  prev: CallbackNode | null;
}
```

这说明 `CallbackNode` 是对象，不是 `setTimeout` 那种数字型 id。

#### 1. `cbNode` 是什么

```typescript
const cbNode = getFirstCallbackNode();
```

- 来源：`getFirstCallbackNode()`
- 含义：Scheduler 当前队列里的首个回调节点（如果没有任务则是 `null`）
- 用途：拿到“当前已在调度队列中的任务”，后续可用于取消

#### 2. `cancelCallback` 是什么

```typescript
cancelCallback(cbNode)
```

- 来源：Scheduler API
- 含义：取消传入的那个 `CallbackNode` 对应的任务
- 用途：当更高优先级任务出现时，先把旧任务从调度队列移除（实现抢占）

#### 3. `curCallback` 是什么

```typescript
let curCallback: CallbackNode | null = null;
curCallback = scheduleCallback(curPriority, performWork.bind(null, curWork));
```

- 来源：`scheduleCallback(...)` 的返回值
- 含义：当前这次调度创建出来的任务节点引用（你自己的变量缓存）
- 用途：
  1. 记录“这次调度对应的是哪一个任务节点”
  2. 在 `performWork` 里和重新调度后的结果比较（`prevCallback === newCallback`），判断是否还是同一个任务在继续

总结：

1. `cbNode`：从 Scheduler 里“读出来”的当前首任务节点  
2. `cancelCallback`：取消某个任务节点的函数  
3. `curCallback`：你自己保存的“当前调度返回的任务节点引用”  

因此 `curCallback` 不是 timerId 数字，而是一个 `CallbackNode` 对象引用。

### Q3: “同优先级不重复发起新调度”是什么场景？我不能点击多次同优先级按钮吗？

可以连续点击同优先级按钮。这个判断不是禁止点击，而是避免重复创建同优先级调度回调。

`if (curPriority === prevPriority) return;` 的作用是：当前已经有同优先级任务在调度链路里时，不再重复执行 `cancel + scheduleCallback`。

典型场景：

1. 当前正在执行 `NormalPriority` 的 `performWork`
2. 用户又连续点击多次 `NormalPriority` 按钮
3. 每次点击都会触发 `schedule()`

如果没有这句判断，就会反复发生：

1. `cancelCallback(cbNode)` 取消旧回调
2. `scheduleCallback(...)` 重新创建同优先级回调

这会产生无意义的调度开销。

有这句判断之后：

1. 新点击产生的 `work` 仍会进入 `workList`（不会丢任务）
2. 当前同优先级回调继续执行，不重复创建新回调
3. 当前任务完成后，`schedule()` 会继续从队列取下一个任务执行

所以它的语义是：

1. 同优先级：复用当前调度链路，减少抖动和开销
2. 更高优先级：才取消旧回调并重新调度，实现抢占

### Q4: `performWork` 里 106-112 行的这段代码是什么意思？有什么作用？

```typescript
const prevCallback = curCallback;
schedule();
const newCallback = curCallback;

if (newCallback && prevCallback === newCallback) {
  return performWork.bind(null, work);
}
```

这段代码的作用是：**在一次 `performWork` 执行结束时，判断"下一步是否继续当前 work"，还是"切换到别的调度任务"**。

#### Scheduler 的回调执行机制

当你调用 `scheduleCallback(priority, callback)` 时，Scheduler 会在某个时间片执行这个 `callback`。

**关键点：** `callback` 执行完后，可以返回两种结果：

1. **返回 `undefined` 或不返回**：表示任务完成了，Scheduler 不会再调用它
2. **返回一个新函数**：表示"任务没做完，下次继续执行这个返回的函数"

#### 逐行解释

- `const prevCallback = curCallback;`  
  记录"调用 `schedule()` 之前"的当前调度节点引用
  
- `schedule();`  
  重新跑一遍调度策略（检查队列、优先级、是否取消旧任务、是否创建新回调）
  
- `const newCallback = curCallback;`  
  取"调用 `schedule()` 之后"的调度节点引用
  
- `if (newCallback && prevCallback === newCallback)`  
  判断：`schedule()` 后调度节点是否变化
  - **条件成立**：调度节点没变，还是同一个 callback 负责当前任务
  - **返回 `performWork.bind(null, work)`**：告诉 Scheduler "下次继续执行我"

#### 情况 1：任务没做完 且 没有更高优先级插队

```javascript
// 假设当前在执行 NormalPriority 的 work
performWork(work) {
  while (!shouldYield() && work.count) {
    work.count--;  // 假设做了 50 个，还剩 50 个
  }
  // 时间片用完了，跳出 while
  
  prevCallback = CallbackNode_A (当前的 NormalPriority 回调)
  schedule();  
  // schedule() 发现：还是 NormalPriority 最高，没有更高优先级
  // 所以 curCallback 没变，还是 CallbackNode_A
  newCallback = CallbackNode_A
  
  if (newCallback && prevCallback === newCallback) {  // true!
    return performWork.bind(null, work);  // 告诉 Scheduler："下次继续执行我"
  }
}
```

**结果：** Scheduler 在下一个时间片会继续执行 `performWork(work)`，把剩下的 50 个做完。

#### 情况 2：执行过程中，来了更高优先级任务

```javascript
// 假设当前在执行 NormalPriority 的 work
performWork(work) {
  while (!shouldYield() && work.count) {
    work.count--;  // 假设做了 50 个，还剩 50 个
  }
  // 时间片用完了
  
  prevCallback = CallbackNode_A (NormalPriority)
  schedule();  
  // 这时 workList 里有个新的 ImmediatePriority 任务
  // schedule() 发现优先级更高，会：
  //   1. cancelCallback(CallbackNode_A)
  //   2. curCallback = scheduleCallback(ImmediatePriority, ...)
  // 此时 curCallback 变成了新的 CallbackNode_B
  newCallback = CallbackNode_B
  
  if (newCallback && prevCallback === newCallback) {  // false!
    return performWork.bind(null, work);
  }
  // 条件不满足，不返回，函数结束
}
```

**结果：** 
- Scheduler 不会继续执行 NormalPriority 的 work
- 转而执行 ImmediatePriority 的任务
- NormalPriority 的 work 暂停（`work.count` 还剩 50），等后续重新调度

#### 核心总结

这是 Scheduler 的"任务续跑"机制：

- **返回函数** = "我还没做完，下次继续"
- **不返回** = "我让位给别的任务了"

通过比较 `prevCallback === newCallback` 来判断：
- **相等**：调度没变化，继续当前任务（返回续跑函数）
- **不等**：调度变了（更高优先级来了），不返回，让位

### Q5: 关于任务打断和恢复的两个疑问

#### Q5.1: `cancelCallback(CallbackNode_A)` 会销毁 `CallbackNode_A` 吗？被打断的任务后续怎么重新调度？

`cancelCallback(CallbackNode_A)` **不会销毁 `work` 对象本身**，只会把 `CallbackNode_A` 从 Scheduler 的调度队列中移除。

**关键点：`work` 和 `CallbackNode` 是两个东西**

```typescript
// work 对象（你的业务数据）
const work = { count: 50, priority: 3 };  // 在 workList 里

// CallbackNode（Scheduler 的调度节点）
const callback_A = scheduleCallback(3, performWork.bind(null, work));
```

- `work` 对象一直在 `workList` 里，`cancelCallback` 不会动它
- `cancelCallback` 只是把 Scheduler 内部的回调节点移除，不再执行那个回调

**被打断后如何恢复：**

```typescript
// 场景：NormalPriority 执行到一半
performWork(work) {  // work.count 还剩 50
  // ...
  prevCallback = CallbackNode_A (NormalPriority)
  schedule();
  // schedule() 里发生了：
  //   1. cancelCallback(CallbackNode_A)  ← 只是取消调度，work 还在 workList
  //   2. 发现更高优先级，创建新回调
  newCallback = CallbackNode_B (ImmediatePriority)
  
  // prevCallback !== newCallback，不返回续跑函数
  // 函数结束，NormalPriority 的 work 暂停
}

// 此时：
workList = [
  { count: 50, priority: 3 },   // NormalPriority，还剩 50（没被删除！）
  { count: 100, priority: 1 }   // ImmediatePriority（正在执行）
]
```

**ImmediatePriority 执行完后：**

```typescript
performWork(immediatePriorityWork) {
  while (...) {
    work.count--;  // 做完了，count = 0
  }
  
  if (!work.count) {
    workList.splice(...);  // 从 workList 移除这个 work
    prevPriority = IdlePriority;
  }
  
  schedule();  // ← 关键：再次调度
}

// schedule() 执行：
function schedule() {
  const curWork = workList.sort(...)[0];  
  // 此时拿到的是 { count: 50, priority: 3 }（之前被打断的那个）
  
  curCallback = scheduleCallback(3, performWork.bind(null, curWork));
  // 创建新的调度，继续执行剩下的 50 个
}
```

**总结：**
- `cancelCallback` 只取消 Scheduler 的回调，不删除 `work` 数据
- `work` 一直在 `workList` 里等待
- 高优先级任务完成后，`schedule()` 会重新从 `workList` 取出被打断的 `work` 继续执行

#### Q5.2: `return performWork.bind(null, work)` 是由 Scheduler 自动调用执行的吗？

**是的，由 Scheduler 自动调用。**

Scheduler 的回调类型定义：

```typescript
type FrameCallbackType = () => FrameCallbackType | void;
```

这个类型说明：
- 回调函数可以返回 `void`（不返回）
- 也可以返回另一个 `FrameCallbackType` 函数

**Scheduler 内部逻辑（简化）：**

```typescript
function workLoop() {
  let currentTask = taskQueue[0];
  
  while (currentTask) {
    const callback = currentTask.callback;
    const continuationCallback = callback();  // 执行回调
    
    if (typeof continuationCallback === 'function') {
      // 如果返回了函数，更新当前任务的回调
      currentTask.callback = continuationCallback;
      // 下一个时间片继续执行这个 continuation
    } else {
      // 没返回函数，任务完成，从队列移除
      taskQueue.shift();
    }
    
    if (shouldYield()) break;  // 时间片用完，让出控制权
    currentTask = taskQueue[0];
  }
}
```

**在你的代码里：**

```typescript
function performWork(work: Work, didTimeout?: boolean) {
  while ((needSync || !shouldYield()) && work.count) {
    work.count--;
  }
  
  const prevCallback = curCallback;
  schedule();
  const newCallback = curCallback;
  
  if (newCallback && prevCallback === newCallback) {
    return performWork.bind(null, work);  // ← 返回给 Scheduler
  }
  // 不返回（返回 undefined）
}
```

**执行流程：**

1. Scheduler 调用 `performWork(work)`
2. `performWork` 执行一部分，时间片用完
3. `performWork` 返回 `performWork.bind(null, work)`
4. Scheduler 收到这个返回值，知道"任务没完成"
5. Scheduler 在下一个时间片**自动调用**这个返回的函数
6. 继续执行 `performWork(work)`，直到 `work.count === 0` 或被更高优先级打断

**一句话总结：** 你返回函数，Scheduler 自动在下次时间片调用它。这是 Scheduler 实现任务续跑的核心能力。

### Q6: `cancelCallback` 删除了 Scheduler 链表节点，为什么被打断的任务还能恢复？

因为 `workList` 和 Scheduler 内部队列是**两个完全独立的数据结构**，`cancelCallback` 只影响 Scheduler 队列，不会删除 `workList` 里的数据。

#### 两个独立的队列

**1. `workList`（你的代码维护的数组）**

```typescript
const workList: Work[] = [];  // 你自己定义的业务队列
```

- 存放 `{ count: 50, priority: 3 }` 这样的 `work` 对象
- `cancelCallback` **不会**操作这个数组
- 只有你代码里的 `workList.unshift()` 和 `workList.splice()` 会修改它

**2. Scheduler 内部的任务链表**

```typescript
// Scheduler 内部（你看不到的实现）
taskQueue = [CallbackNode_A, CallbackNode_B, ...]
```

- 存放 `CallbackNode` 对象（包含 `callback`、`priorityLevel`、`expirationTime` 等）
- `cancelCallback` 操作的是**这个链表**
- `scheduleCallback` 和 `cancelCallback` 会修改它

#### 完整流程示例

**1. NormalPriority 被打断时**

```typescript
// workList（你的队列）
workList = [
  { count: 50, priority: 3 }  // NormalPriority，执行到一半
]

// Scheduler 队列
taskQueue = [
  CallbackNode_A {
    callback: performWork.bind(null, work),
    priorityLevel: 3
  }
]
```

**2. ImmediatePriority 来了，执行 `schedule()`**

```typescript
function schedule() {
  const cbNode = getFirstCallbackNode();  // 拿到 CallbackNode_A
  
  // workList 现在有 2 个任务
  workList = [
    { count: 50, priority: 3 },    // 旧的 NormalPriority
    { count: 100, priority: 1 }    // 新的 ImmediatePriority
  ]
  
  const curWork = workList.sort(...)[0];  
  // curWork = { count: 100, priority: 1 }（ImmediatePriority 优先级更高）
  
  cancelCallback(cbNode);  // ← 只删除 Scheduler 队列里的 CallbackNode_A
                           // workList 里的 { count: 50, priority: 3 } 还在！
  
  curCallback = scheduleCallback(1, performWork.bind(null, curWork));
}
```

**此时状态：**

```typescript
// workList（没变！）
workList = [
  { count: 50, priority: 3 },    // 还在
  { count: 100, priority: 1 }    // 还在
]

// Scheduler 队列（变了）
taskQueue = [
  CallbackNode_B {  // 新的，对应 ImmediatePriority
    callback: performWork.bind(null, { count: 100, priority: 1 }),
    priorityLevel: 1
  }
]
// CallbackNode_A 被删除了
```

**3. ImmediatePriority 执行完，恢复 NormalPriority**

```typescript
performWork({ count: 100, priority: 1 }) {
  while (...) {
    work.count--;  // 执行完，count = 0
  }
  
  if (!work.count) {
    workList.splice(...);  // 从 workList 删除 ImmediatePriority 的 work
    // workList 现在只剩：[{ count: 50, priority: 3 }]
  }
  
  schedule();  // ← 再次调度
}

function schedule() {
  const curWork = workList.sort(...)[0];
  // curWork = { count: 50, priority: 3 }  ← 从 workList 里拿到！
  
  curCallback = scheduleCallback(3, performWork.bind(null, curWork));
  // 创建新回调，继续执行剩下的 50 个
}
```

#### 操作对比表

| 操作 | 影响 `workList` | 影响 Scheduler 队列 |
|------|----------------|-------------------|
| `workList.unshift(work)` | ✅ 添加 | ❌ 不影响 |
| `workList.splice(...)` | ✅ 删除 | ❌ 不影响 |
| `scheduleCallback(...)` | ❌ 不影响 | ✅ 添加 CallbackNode |
| `cancelCallback(cbNode)` | ❌ 不影响 | ✅ 删除 CallbackNode |

#### 核心总结

- `cancelCallback` 删除的是 **Scheduler 的 CallbackNode**（调度节点）
- `workList` 里的 **work 对象**（业务数据）不受影响
- 被打断的任务数据一直在 `workList` 里，等待下次 `schedule()` 重新取出并调度
