### 步骤 1:新增并发更新同步调度示例脚本，构建 `workList -> schedule -> perform` 闭环

**路径:** `demos/test-fc/main.ts`

**修改内容:**
1. 新增 `Work` 类型和 `workList` 队列，作为待执行任务容器
2. 新增 `schedule()`，每次从队列中取出任务并分发给执行阶段
3. 新增 `performWork()`，在循环中消耗 `count` 并持续插入 `span`，模拟 render/commit 连续推进
4. 新增 `insertSpan()`，将执行结果实时写入 `#root`
5. 新增按钮点击触发逻辑，交互后向队列压入任务并启动一次调度
6. 补充样式导入，确保大量 `span` 输出时可换行展示

**关键代码:**

```diff
// demos/test-fc/main.ts
import './style.css';

const button = document.querySelector('button');
const root = document.querySelector('#root');

interface Work {
  count: number;
}

const workList: Work[] = [];

function schedule() {
  const curWork = workList.pop();
  if (curWork) {
    performWork(curWork);
  }
}

function performWork(work: Work) {
  while (work.count) {
    work.count--;
    insertSpan('0');
  }
  schedule();
}
```

## 第三部分:主要知识点

### 1. 当前同步更新链路的驱动方式

本节课围绕的问题是：当前实现是如何被驱动起来的。截图给出的同步链路可以抽象为一个循环：

1. 交互触发更新
2. 调度阶段执行微任务调度（`ensureRootIsScheduled`）
3. 微任务调度结束后进入 render 阶段
4. render 阶段结束后进入 commit 阶段
5. commit 阶段结束后再次回到调度阶段（`ensureRootIsScheduled`）

核心结论是：当前实现整体由一个大的微任务循环驱动，循环的入口与续航点都在调度模块。

---

### 2. 同步示例的结构与阻塞来源

截图中的同步示例由三段组成：`workList`（任务容器）-> `schedule`（取任务并调度）-> `perform`（执行任务）。

它直观展示了“执行完继续调度”的闭环，但也带来两类阻塞风险：

1. `work.count` 数量过多
2. 单个 `work.count` 对应的工作量过大

一旦 `perform` 长时间占用主线程，后续任务和交互响应都会被延后，这也是同步模型的主要瓶颈。

---

### 3. 并发更新的理论基础：时间切片

截图明确给出并发更新的基础是“时间切片”。

可以把它理解为：不再要求一次性做完整个大任务，而是将任务拆成可中断、可恢复的多个时间片段。在片段边界处，调度器可以让出执行权，优先处理更紧急的工作，从而提升交互响应能力。

---

### 4. 从“微任务循环”到“Scheduler 驱动循环”的改造方向

改造示例强调：如果希望在任务中完成任务调度，本质上要把驱动循环从“纯微任务续跑”升级为“由 `Scheduler` 驱动的宏任务循环”。

这意味着：

1. 调度职责从单一微任务阶段扩展到调度器统一管理
2. 执行流程允许在片段间被打断与续跑
3. 系统不再只有“是否执行”的维度，而是引入“先执行谁”的决策能力

---

### 5. Scheduler 的五种优先级

截图列出的优先级层级如下（由高到低）：

1. `ImmediatePriority`
2. `UserBlockingPriority`
3. `NormalPriority`
4. `LowPriority`
5. `IdlePriority`

这组优先级为并发调度提供了基础策略：高优先级任务先执行，低优先级任务延后或分片执行，空闲任务在系统不繁忙时再处理。
